## Essential addition: acknowledge same-key resurrection before physical PUT

The following sequence defeats an acknowledgment written only in the catalog row **after** physical PUT:

1. At generation g, K is durably in eligible manifest debt. Actual retirement deletes K successfully. Its page still contains K with appliedGeneration < g. Native holds a valid opaque all-success proof for g.
2. A caller uploads K again at the same generation. Physical R2 PUT succeeds, but the page/ack write or its sync fails. The DO marks itself dirty, then evicts or restarts.
3. Reopening recovers the old page and current debt. An old valid proof still matches g and the debt digest, and the durable acknowledgment remains < g. Applying it removes K from the catalog/exact live view even though K now exists physically.

The same-row acknowledgment protects reuploads whose catalog write became durable. It does not prove the absence of a later physical mutation that happened before the acknowledgment became durable. R11's mandated PUT-before-catalog order makes this gap real. A correct Native marks the ambiguous operation dirty and performs full GC before its next request, but that behavior alone is not proof replay safety for arbitrary authenticated direct callers or externally replayed valid proofs after eviction.

The minimal bounded fix is exceptional: **when an uploaded key belongs to current eligible debt, first reconcile and durably write/sync that debt's retirement acknowledgment, then issue the actual R2 PUT.** On failed/ambiguous preflush, do not start the physical PUT. The eventual successful upload still receives its normal post-PUT catalog/peak write and pre-CAS sync. This can add a row write for resurrection cases; charge it. In the audited normal windows the next new upload can still fold retirement into its existing post-PUT write when its key is outside debt. Include the exceptional preflush in scalar, fused, older-Native and direct-caller paths. A same-page optimization cannot waive it merely because K's bytes/hash are immutable.

Required fault case: delete K/prove absence, begin same-generation PUT(K), inject a failure after actual R2 success but before its catalog write and before/at final sync, evict, then replay the old proof. Verify physical K remains cataloged or full recovery is mandatory; never certify absence. Repeat before/after the new preflush barrier, with another registration, GC and page splits.

The retained older system has a separately documented R2-PUT-before-catalog orphan gap dependent on Native dirty/startup recovery. Do not silently claim that this protocol repairs arbitrary uncataloged PUTs after complete process loss. The preflush above prevents the new absence proof from authorizing the specific same-key replay failure.

## Exact state and durability requirements

Use three distinguishable states, not a single boolean that proofs can clear:

- **Exact:** volatile membership/live totals match the physical catalog; a bounded set of confirmed retirements may remain absent only from the persisted page.
- **Only current debt unresolved:** reopening discovered current manifest eligible debt intersecting a page whose acknowledgment is older than the manifest generation. Only those bounded members have unresolved physical presence. Their stale durable bytes are historical evidence, not exact current live bytes.
- **Arbitrary uncertainty:** PUT, catalog, transaction, sync, decoding, duplicate-membership or underlying R2 ambiguity invalidated the view. Retain R11 dirty-to-generation-checked-full-GC recovery. An absence proof or a few debt HEADs cannot clear this state.

R11 constructor/reload (`index.js:487–497,577–589`) currently loads SQL live totals and initializes certainty. R13 must examine the authoritative durable manifest and page acknowledgment before allowing another physical PUT or deriving its temporary peak. Charge that actual manifest read and every cursor. A proof can resolve only the second state. A general SQL reload must not reset arbitrary uncertainty on the same instance. Invalid/unknown/dead-session proof must have a productive charged fallback rather than permanent 409/retry behavior.

For ordinary all-success retirement, keep exact volatile live bytes/count and bounded successful-key outcomes immediately after actual deletes. Leave the pre-delete persisted page and H intact. Current durable garbage plus intersecting page membership identifies unapplied potential debt; garbage never proves physical absence. Keep at most the retained 256 keys/outcomes and decode/update one page at a time, without a repository-wide object cache.

Flush pending survivors before any publication can replace/drop that durable debt marker, including a no-upload CAS; before another independent retirement set; before using an unrelated-page PUT; and on overflow/split or mixed representations requiring an eager path. All relevant old pages must be acknowledged durably before publishing the new manifest. When current debt has no intersecting catalog members, no physical uncertainty follows merely from a nonempty garbage list. A page already acknowledged at g must not treat its later reuploaded members as old debt again.

Keep the retained barriers: actual successful PUT → catalog/peak persistence → successful sync → CAS; winning CAS → successful sync → actual retirement DELETEs in original order. Deferral changes only a normal survivor-map persistence point. It cannot delay R2 deletes, alter outcomes, move CAS before the upload barrier, or hide a final queue beyond observation.

H remains a durable historical maximum. Updating a surviving page carries max(old page H, current H, exact physical temporary live bytes). Empty-page deletion must preserve/sync a sufficient witness first, excluding the **union** of all doomed legacy/page rows; doomed pages cannot witness each other. A bounded all-success set that would remove its last carrier can simply take the eager checkpoint path. GC still preserves the entire authoritative pre-delete physical inventory/orphan peak before destructive work and rebuilds transactionally with actual charges.

Partial/failed/unknown retirement takes the R12 eager/dirty path and gets no proof. Do not convert catalog/sync ambiguity into a clean successful batch. Native's pre-publication dirty assignment (`native.rs:1181`) and failed-debt dirty state (`:1216`) must continue through error paths. Any new deferred recovery or physical mutation that occurs earlier in receive must have dirtied Native before an ambiguous error can escape. Correctness cannot rely only on a later publication assignment.

## Proof protocol and source integration

A private per-registration HMAC key is appropriate if never returned to Native and distinct from the existing generation-witness key, which is intentionally returned (`index.js:364–370`). Bind an explicit domain/version, repo, private registration session, safe generation and SHA-256 of the **entire exact ordered eligible debt set**, excluding live representations. Use one unambiguous canonical encoding in issuer and DO; validate duplicate keys and exact order, with retained 256-key cap. Hashing a selected page subset is insufficient.

Mint only from the trusted actual DO response for the matching request. Verify a durable winning publication, correct uploaded member for fused upload, exactly one ordered outcome per eligible debt key, all outcomes true, all expected real DELETE attempts/successes, and a valid fully known per-RPC receipt. Never accept a Native-supplied receipt as minting evidence. A lost/malformed/partial response does not earn a proof.

Concrete integration work is necessary: `acceptReceipt` (`index.js:262–316`) currently permits NULL SQL counters, and `dispatchService` (`:341–355`) discards the parsed receipt and strips its header. A valid ordinary receipt is not automatically mintable evidence. Return the validated parsed receipt to a private issuer path, require SQL rows to be known for minting, and count it **exactly once before** crypto/body processing can fail. Keep actual attempts/failures/bytes and unknown SQL visibility intact if proof creation or body validation fails. Do not dispatch again to recreate the receipt.

Keep the retirement JSON response shape unchanged. Native response structs explicitly deny unknown fields (`cloudflare.rs:195–236`); a new body field would break older clients. A bounded response header and one bounded opaque Native cache are a coherent extension. Strictly parse token syntax/version/length and reject oversized values before I/O. A binary 89-byte token (version 1, session 16, generation 8, debt digest 32, MAC 32) can fit in 120 base64 characters; add its actual fixed/dynamic overhead to the Native retained allocation budget rather than assuming the illustrative 128-byte cache covers arbitrary text encoding. Keep the header's explicit small cap, e.g. 512 bytes.

On authenticated service ingress, strip every private header before verification/trusted injection, including mixed casing via normalized Headers; strip on public gateway ingress too. Worker verifies the opaque token against the current private repo/session key, then injects a private verified confirmation. DO independently checks current manifest generation/debt and per-page acknowledgment. No public request/proof may replace the retained authoritative generation read. In-flight re-registration/key rotation invalidates old tokens and safely falls back; do not remint an old receipt under an unrelated newer session accidentally.

Registry/isolate loss is real: `CODEC_ORIGIN` fallback (`index.js:446`) can keep the same Native process reachable without a new registration/startup recovery. Absent/stale/wrong-repo/wrong-session/malformed proof therefore must fall back to charged bounded actual HEADs for debt-only uncertainty, or a supported generation-checked Native GC path. HEAD absence is established only by a successful authoritative null result; errors stay unresolved. Arbitrary underlying uncertainty remains full GC. Worker key/session state remains bounded by the existing 256-registration cap, and no key is persisted or assumed to survive another isolate without explicit implementation.

## Codec, acknowledgment and compatibility

The 14 + 32×36 = 1,166-byte v2 representation fits below the retained 1,286-byte serialized page cap and retains 32 members. Precisely specify magic/version/count, uint64 generation endianness and u32 size endianness. Validate exact length, count 1–32, sorted unique digests, correct routing prefix, aggregate row size, safe generation before Number conversion, and each size in **0..16 MiB inclusive**. Zero bytes is a valid scalar content-addressed PUT even though fused upload requires positive length. Reject malformed values before mutation.

Decode durable v1/v2 page formats irrespective of registry capability. Existing v1 pages have no acknowledgment and need bounded reconciliation before their first v2 acknowledgment in a debt-bearing store. A simple length-only constructor formula from R12 will not count both codecs correctly; dispatch on validated durable format and preserve exact member counts. New pages initialize acknowledgment at the current generation; splits propagate the parent acknowledgment; GC rebuilds acknowledge the reconciled current generation. Empty pages do not survive as unbounded tombstones. An already-applied proof is a no-op on that page.

A distinct Native/registration capability must opt into deferral and proof support. Fresh older v1/v2/v3 providers sharing the Worker retain their immediate path and charged schema behavior. On an existing deferred store, an older Native or lost capability still requires proper durable decoding and charged debt recovery before mutation. Source/lineage identity for the ACK Native must be genuinely distinct. Worker rollback to code unable to decode v2 remains unsupported. Adding a nullable acknowledgment SQL column instead would require separately measured DDL/cursor/storage costs and is not assumed free.

- Valid, absent, malformed, oversized, stale, wrong-repo/session/generation/debt proofs; duplicate token/JSON members; old debt members and adversarial splice/order changes; key/session loss and concurrent re-registration; valid-empty scalar PUT; generation limit handling.

Metrics can report actual physical inventory and durable H, but its excluded LIST cannot mutate production certainty. Reads do not flush.
