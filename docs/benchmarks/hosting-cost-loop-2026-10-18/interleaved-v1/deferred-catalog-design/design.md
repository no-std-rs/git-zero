# After-pages known-cost audit: one further bounded candidate remains

**Finding:** do not claim a plateau after conditionally viable catalog pages. A concrete next design can eliminate the seven normal post-retirement page writes per profile by folding confirmed removals into the next already-required upload catalog write. Its four-profile gross saving is **28 written rows / $0.028 per 1,000 repetitions**. This is a conditional design projection, not an implemented or measured saving. Exact recovery requires explicit dirty state, fully charged recovery, and durable replay protection. The naive version that trusts manifest garbage as proof of physical deletion is invalid.

This bounded independent audit made no source edits, builds, tests, service calls, network requests, pushes, or benchmarks. It read frozen source at `7e7856a3f6c279a8f97956a4475cb12f847b1f7e`, the two earlier design reports, and existing complete fresh R8 reports from run 39087721879. Only audit artifacts were created under `/tmp`; `jq` performed offline report arithmetic. No MJS or other new execution runner was used. R9–R11 and pages remain unmeasured for purposes of this report. Current incomplete or noisy screens are not stopping evidence.

## Candidate A: bounded deferred survivor updates with paid recovery

Use deferral only for the existing fused retirement path, after **winning CAS and its sync**, and only for a bounded manifest retirement set. Actual R2 DELETEs still happen immediately, in existing order, with exact per-key outcomes and attempts. The normal all-success path keeps the resulting live deltas in bounded volatile bookkeeping instead of rewriting the page immediately. The stale durable page remains a valid historical peak witness, but is explicitly not certified physical inventory. Manifest garbage authorizes deletion and detects potential staleness; it does not prove success.

Before the next actual PUT, combine the pending successful removals and the new member in one page write, preserving `peak >= max(old peak, exact physical pre-CAS temporary live bytes)`, then sync before CAS. For the one-root-page normal workload this is the same one written row already needed for the PUT. The physical set and peak are unchanged. The durable pre-delete page has the same at-most-11/13-member shape as the earlier page design; keeping it until the next PUT does not create 32-entry overflow on this trace.

The implementation needs all of the following invariants:

- Keep at most the existing 256 retirement keys/outcomes, and process one bounded page at a time. There is no repository-wide object cache or unbounded list of retired pages. Repeated retirements without upload must flush older debt before accepting a new bounded set. Scalar DELETEs without a durably published retirement marker retain immediate catalog persistence.
- Before any publication can drop or replace the durable debt marker, flush its confirmed removals, even when that publication has no PUT. When a next PUT touches another page, flush other pending pages and charge those actual writes; no claim that arbitrary traces save all page writes. Overflow, page split, mixed legacy rows, and empty pages use explicit bounded eager paths. A normal all-success root-page queue is empty by the generation-30 upload and remains empty at final observation.
- Do not erase the last historical peak witness. A nonempty rewritten page carries its old peak. If all witnesses can disappear, preserve and sync the full doomed-set peak first, as required by the independent page review. The union-of-doomed-witness rule still applies. GC retains the entire physical pre-delete inventory/orphan peak rule.
- Partial physical failures cannot be represented as universal success. Prefer the existing eager survivor rewrite/dirty recovery path for partial outcomes, with every actual row charged; Native keeps failed debt dirty and recovers. A catalog/sync ambiguity is a bridge failure, not a clean deletion receipt. Native must become dirty before an ambiguous new mutation/recovery can escape the receive path; do not rely only on the existing later `view_dirty = true` just before publication.
- At DO construction, decode durable page state independently of capability/registry state and inspect the authoritative current manifest. If unapplied debt intersects catalog membership, mark only those members' physical presence unresolved. Do not use their stale bytes/count as exact live totals or a basis for the next upload peak. Other arbitrary catalog uncertainty still requires authoritative full recovery.
- A valid next mutation can resolve this bounded deletion uncertainty by actual HEADs before any new physical PUT, update a volatile exact view, then merge it into the required upload write. Failed/ambiguous HEADs must not certify absence. This can occur within the existing mutation RPC: there is no necessary extra Worker or DO callback and no new protocol merely to avoid a permanent 409/retry wedge. Direct caller GC and Native crash/restart recovery remain supported, fully charged alternatives.
- Reads perform no migration, SQL repair, or deferred flush. Metrics may report its actual inventory and durable peak but **must not** use its excluded observer LIST to clear dirty state, rebuild the volatile production catalog, or avoid a later paid recovery. Reads/metrics are never evidence that a stale page is physically exact. A production recovery triggered during a read would need actual Class B HEAD receipts; a LIST on an ordinary read violates the retained Class A guard. The simpler policy is to delay bounded recovery until the next valid mutation.

Recovery has a real price. Three HEADs for one reopened window cost **$0.00108** in the repeated objective, plus actual SQL reads and any required row writes. Reopening every four-profile retirement window would add **$0.03024**, exceeding $0.028 gross. A LIST per window adds $0.126 before reset writes; full GC resets make that worse. Those are not free startup/observer work.

Let W, R, H, L, C be additional actual written rows, read rows, HEAD/GET calls, LIST calls and paired Worker+DO callbacks per four-profile replay relative to pages, with no changed byte/storage component. Net saving is

`$0.028 - .001 W - .000001 R - .00036 H - .0045 L - .00045 C`.

At the illustrative denominator the 1% budget permits only **$0.0096318556382** overhead: at most 26 HEADs, or eight complete three-HEAD windows, absent other costs. Two LISTs already cost $0.009 before reads/reset writes; three fail the 1% target. The archived 56 windows have zero observed reopen transitions and therefore do not imply these extra normal calls, but their absence is not a recovery guarantee or a measured candidate saving. Constructor/debt reads must be charged, including a new manifest row read where not already present.

## Candidate B: proof handoff across DO eviction, with durable replay protection

A bounded protocol extension can avoid HEADs when the DO evicts but the Worker registration and Native process survive. This is separate from Candidate A and is not present in current source.

The authenticated Worker may sign an opaque all-success retirement proof after validating the actual DO response and complete per-RPC accounting receipt. Use a **new private per-registration HMAC key never returned to Native**, distinct from the existing generation-witness key (which Native knows). Bind a domain/version, repository, private registration session, authoritative generation, and SHA-256 of the exact canonical ordered eligible debt set. The Worker signs only after all required actual deletes succeeded/confirmed absence, CAS was durable, and the reply is unambiguous. Do not mint a proof from a Native-provided receipt or after an unknown/malformed usage receipt. Native stores one bounded opaque proof and returns it on a later existing service call/PUT; no extra priced callback is required. Set an explicit small header limit, such as 512 bytes, and reject oversized proof syntax before I/O.

The Worker strips spoofed private headers, verifies the proof, then injects its trusted internal confirmation. The DO independently checks current generation and the exact debt digest before using it. A valid proof can establish physical absence of the retired set without HEADs; it cannot certify arbitrary catalog uncertainty or a failed/uncataloged PUT. The eventual catalog change is still in the next required upload row write/sync. Ordinary public Git requests still perform the same authoritative generation read. The proof does not replace that obligation.

**Essential replay fault:** generation plus debt digest is insufficient. Suppose proof for generation g confirms deletion of K; a PUT then reuploads K while g has not advanced. Replaying the old proof must not remove K's new catalog member. Add a durable per-page **applied retirement generation** to the same upload page write. Apply a proof or HEAD reconciliation only to pages with an older applied generation. New pages initialize at the current generation; splits and GC rebuilding propagate it; a proof already applied is a no-op. Every PUT, including scalar/direct/older-Native mutations, must resolve and acknowledge older pending debt before reintroducing its keys. No separate acknowledgment row/write may be hidden.

Simply appending eight header bytes to the original page codec would make its maximum 1,294 bytes and exceed the proposed 1,286-byte ceiling. A concrete codec-v2 option keeps both existing limits: a 14-byte magic/version/count/applied-generation header plus 32 entries of 32-byte digest and four-byte size totals **1,166 bytes**. This uses the retained public chunk cap of 16 MiB; reject decoded size outside `0..MAX_BLOB_BYTES`, validate uint64 generation before safe Number conversion, sorted uniqueness and exact length. Zero-length scalar PUT is valid and must remain representable; staged upload's positive length is a separate rule. Mixed v1/v2 decoding is mandatory; v1 requires bounded recovery before obtaining its first applied generation. A nullable SQL acknowledgment column is another design but requires its own charged ALTER and actual SQLite guard. Neither a larger page BLOB nor an unpriced schema change is assumed.

Required fault cases include K deleted/proof issued, K reuploaded at the same generation, proof replayed both before and after DO eviction; eviction before versus after the folded catalog sync; another scalar/older-Native PUT reintroducing K; proof replay after GC or split; and generation advancement that replaces debt without a PUT. Verify the physical K remains represented, temporary peak is exact, replay never repeats removal, every recovery HEAD remains charged, and no observer changes the result. Also verify old Native on new Worker reads and mutates existing deferred v2 state through charged recovery even when its fresh registration does not negotiate deferral. Fresh old-client namespaces retain their negotiated legacy/page path. The changed codec/protocol and actual SQLite page usage require independent review and real tests.

Do not assume a trusted ephemeral registry survives another Worker isolate, process restart, unregister, or re-registration. Key/session loss invalidates proof; missing/invalid/stale proof must gracefully use charged bounded HEAD recovery or generation-checked Native GC, not accept garbage as proof or silently reject every future push. Current `CODEC_ORIGIN` fallback means registry loss alone does not prove startup GC will occur. A concurrent re-registration can invalidate an in-flight proof and therefore needs the same fallback. Worker rollback to code lacking the deferred codec is unsupported; newer Worker/older Native must recover/read/update pending durable state correctly, irrespective of a lost capability flag.

Only all-success outcomes get the proof; partial outcomes use the eager/dirty path. Lost CAS/delete/proof replies preserve Native dirty recovery. Receipt handling must preserve all actual attempts, bytes, failures and SQL unknowns through cryptographic failures too. No metrics observer may mint or apply confirmation from its LIST. HMAC CPU and active duration remain unknown billed dimensions, not free compute inferred from elapsed time. The proof adds bounded protocol/header bytes, and the new page state affects SQLite storage: neither is silently claimed free under an existing cap. The retained proof and bookkeeping must count toward existing Native allocation/cache budgets, trimming other cache storage if necessary. Worker key/session storage stays bounded by the existing 256-registration cap. All affected guards require actual validation.

With those gates, Candidate B is a credible bounded next design: same real R2 operations/pack layout/codec output in normal operation, $0.028 gross row opportunity, no new normal callback, and recovery proof carried on existing calls. It is not a demonstrated >1% net saving until a clean implementation, fault review and independent fresh screen price its actual reads/schema/physical accounting. Candidate A alone is credible under the archived residence pattern but not a robust >1% bound over arbitrary eviction schedules.

## What is and is not bounded afterward

Within the retained scalar/fused-upload RPC boundaries, each of the **132 successful physical PUT callbacks** must persist its catalog/peak witness and sync before the CAS that could publish it. Each of **128 winning generation updates** needs a separate durable CAS after that barrier. Co-locating both records in one SQL row does not combine writes separated by those required barriers. This gives a conditional **260 normal row-write floor**, before actual migration/fallback/recovery, once retirement survivor updates are amortized. It is not a global SQL lower bound for a different staging API or persistence model.

The earlier exact audit established zero callback benefit from unordered bulk binning in all 704 whole snapshots and projected R10 selected snapshots. Eliminating all remaining baseline SQL reads and all R2 retention saves only $0.00432443618, below 1%. Those narrow knobs do not justify another optimization round. They do not bound representations, selective reconstruction/index codecs, container layouts or topology changes.

An external Native gateway still requires one authoritative generation read for every public Git request under the retained hybrid contract. There are 704 public gateway requests across the four profiles. Eliminating their Worker and accompanying DO requests would nominally touch $0.3168, but a direct Native endpoint or self-contained Worker codec is a different architecture and must replace authority, authentication, resource and compute accounting. This is an illustrative priced ceiling for that component, not an available micro-optimization. Likewise fewer/different physical chunks, mutable/shared containers or indexed range/object reconstruction change the retained immutable layout or codec and require new physical crash, read/write-byte and peak proofs. None is established viable or rejected globally here.

Worker CPU, DO duration, monthly SQLite storage and Native compute/full bill stay UNKNOWN/NULL. The final SQLite gate is still 24,576 × 1.01 = 24,821.76 bytes; another 4,096-byte page fails. Normal cold latest fetches must retain positive actual GETs and bytes. Existing compressed immutable packs, exact deletion receipts, fixed caps and all original resource/latency guards remain. Do not fit the experiment away with a hidden cache.
