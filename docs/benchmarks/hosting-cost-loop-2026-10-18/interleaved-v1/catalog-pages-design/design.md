# Remaining known-cost audit: a packed catalog page is still viable

**Decision:** there is a concrete next design worth a clean implementation and independent screen after R11. Do not declare a plateau or use one-normalized-row-per-key as a lower bound. Packing a bounded group of catalog entries into one durable SQL row can reduce each ordinary three-key retirement from three written rows to one, with the same real R2 deletes and publication ordering. This is an independently derived design/projection, not a measured saving or a global optimum.

This audit changed no repository source, ran no service/build/benchmark, and made no Git/network calls. It read `/tmp/git-zero-hosting-cost-loop` at reported HEAD `3d54bf0`, the peak proposal, and complete fresh R5–R8 archive `run-39087721879`. All new files are under `/tmp`. ## Bounded schema and routing

Reuse the existing `blob_catalog` table and primary key; add **one nullable `entries BLOB` column** on the first validated mutation authorized by a new `catalog_pages:1` registration capability. Do not create a table/index or materialize an unlimited repository-wide map. Keep existing `size` and `peak_bytes`: for a page, `size` is the sum of member sizes and `peak_bytes` is a historical aggregate peak witness independent of any particular member.

Legacy normalized rows have `entries IS NULL` and their ordinary `chunks/<64 lowercase hex>` key. Page rows use private keys such as `pages/<hex-prefix>`, impossible through the public blob-key validator. Each page holds at most **32 sorted entries**: a six-byte version/count header plus 32-byte digest and eight-byte size per entry, at most **1,286 serialized bytes**. Validate magic/version/count, exact length, strictly increasing unique digests, routing prefix, safe integer sizes and aggregate sum. No blob payload is retained. Fresh normal traces never exceed 13 entries, so remain one root page and have no splits.

Lookup probes the at most **65 hex-prefix ancestors** through primary-key equality, plus the exact legacy key. Prefix-free page leaves mean at most one matching page. There is no scan of every catalog page on ordinary operations. A missing leaf can use two indexed primary-key predecessor/successor queries within the private page-key range; one character beyond the maximum common prefix with those neighbors gives a new prefix disjoint from all existing leaves. If there are no page neighbors, create the root leaf. This avoids a durable directory tree or unbounded routing cache.

On overflow, examine only the full leaf's 32 members plus the new key. Split after their longest common hex prefix into **2–16 nonempty children**; every child has at most 32 entries, even for adversarial common-prefix digests. Atomically delete the old leaf and insert the children with the same or greater peak. At most 17 rows are touched by this exceptional split; charge them. Combined new serialized entry payload is at most `33×40 + 16×6 = 1,416 bytes`, with bounded decode/routing scratch. No repeated one-nibble chain of empty pages is needed.

Delete empty leaves after preserving their peak as described below. Retain no empty directory/tombstone pages. Thus the number of page rows never exceeds represented catalog keys, prefix length is at most 64 characters, and repeated insert/delete churn cannot retain a growing empty routing structure. Sparse pages are permitted; merging is optional and any merge cost must be charged. Constructor inventory can aggregate `SUM(size)`, `MAX(peak_bytes)` and member count from fixed-width BLOB lengths plus legacy rows. It retains the existing once-per-instance catalog scan, not an extra scan per operation.

Do not mass-migrate existing rows: after adding the nullable column, leave legacy rows in place. Existing legacy keys continue updating their legacy row; new keys use pages. Every PUT probes both representations and must establish exactly one membership; a duplicate is an accounting error requiring authoritative reconciliation, never double counting. Serialized mutation, atomic split, and GC reset preserve this invariant by construction. This avoids an unbounded migration transaction and large first-trial rewrite bill. GC may later rewrite surviving inventory into pages using bounded page builders, with actual work fully counted.

## Protocol, durability and failure gates

Use the R11 capability pattern: new Native advertises `catalog_pages:1` in the existing registration; only the trusted registry injects its stripped private header. Registration dispatches no DO call. Fresh old-Native namespaces retain the old schema/behavior. Schema discovery is read-only; **GET, fetch/discovery, metrics, invalid requests and stale GC never migrate or write**. The actual first eligible mutation's ALTER/schema cursor costs belong to that trial, never startup relabeling.

After the entries column exists, the new Worker must understand mixed/page rows regardless of registry flag, lost registry, eviction, restart, or older Native reconnect. Native clients never access SQL directly, so rolling Native backward is supportable. Rolling Worker code back to an implementation that cannot decode pages is not safe and must be documented. Do not gate durable decoding on a transient capability.

On PUT, maintain the exact order: actual successful R2 PUT → one page/legacy catalog update carrying `max(previous peak, true temporary pre-CAS live bytes)` → successful `storage.sync()` → CAS. Split operations share one SQL transaction/barrier. Duplicate immutable PUT adjusts live count/bytes by zero, preserves peak monotonically, and keeps existing real PUT/idempotency behavior. R2/catalog/sync failure never starts CAS or authorizes orphan deletion; invalidate certainty and use the existing dirty recovery path. No new normal HEAD/LIST is justified.

On fused retirement, maintain **durable winning CAS → all required actual R2 DELETE calls** in the original key order → one survivor-map write per touched page → final sync/receipt. Scalar deletion remains supported. A bounded first pass identifies touched pages and whether deleting all requested members could erase the last sufficient witness; preserve/sync the fallback before the first physical delete when necessary. The normal page retains many other entries and its aggregate `peak_bytes` survives unchanged, so no fallback write is required. R2 deletion does not itself erase a SQL peak witness.

Keep the bounded requested-key/outcome bookkeeping (at most 256 keys); decode/read/update one page at a time rather than retaining all page payloads. A second per-page metadata read is acceptable and must be charged. Three normal deletes therefore still perform three real R2 calls, but persist one page survivor map. Failed R2 deletions remain members and false outcomes; confirmed successful deletions are removed. A catalog transaction or ambiguous final barrier must invalidate catalog/live/owner certainty and produce a truthful failure/ambiguous result that makes Native recover before a later mutation. It must not return a clean all-success receipt or let the next PUT derive a new peak from stale overcounted members. This likely needs an explicit bridge error for catalog ambiguity rather than silently translating it into ordinary per-key R2 failure. A conservatively stale durable page is recoverable evidence, not certified physical inventory.

Retain R11's generation-checked GC rule: before physical deletion or resetting catalog rows, durably preserve the maximum of existing fallback/page witnesses, in-memory floor, and the **entire pre-delete authoritative R2 inventory**, including orphans. Partial GC, catalog reset failure, empty repository, restart, and an upload whose SQL write failed must never erase the last historical peak. Reconcile surviving physical keys transactionally and sync. Read-only metrics may observe actual R2 inventory but perform no hidden repair/migration.

## Hard gates before independent measurement

The final SQLite guard is decisive: **24,576 bytes × 1.01 = 24,821.76**; another 4,096-byte page means 28,672 bytes and fails. Reusing the table/index and replacing 13 long normalized keys with a compact 526-byte payload is promising, but no byte/page result is assumed. Actual real-Worker schema mutation, realistic 11/13-key + 33-ref + 11-pack shape, and reopen cases must remain at or below the guard. Do not hide a larger schema in an unpriced table or restore the old layout for the observer.

Rust contracts should cover capability isolation/header spoofing; legacy→mixed and older Native/new Worker reconnect; real cursor counts; duplicate PUT; 32→33 split with adversarial prefixes; lookup gaps; churn to zero; shared live keys; mixed duplicate detection; empty-page last-witness deletion; partial real R2 failures; SQL transaction and sync faults; lost CAS reply; catalog-failed upload orphan; GC reset/restart. Verify exact real R2 attempts/bytes, pre-CAS upload barrier, post-CAS deletes, complete receipts, exact temporary peaks and no writes on reads. A fresh matching two-pair screen follows committed/pushed clean source, then the mandatory final five fresh original-R1/final pairs remain required.

The exact offline bin-packing audit finds **zero** unordered callback savings in every reconstructed whole snapshot and every projected R10 selected snapshot across these 704 rows. Under the unchanged layout, clearing all remaining SQL reads plus all R2 retention would save only $0.00432443618, well below 1%; those isolated knobs cannot justify further work. That conditional observation does **not** cover representation changes such as this page design. Broader shared-object containers, range/index codecs, gateway/DO topology changes or durable metadata co-location are separate designs with different integrity, write-byte and crash obligations; no claim of an exhausted global design space is made.
