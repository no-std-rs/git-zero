## Token and transaction structure

1. Planning runs no Git process, materialization, GC, PUT, CAS, DELETE or reference mutation. It validates the entire current manifest and exact all-pack ordered descriptors. It requires clean state plus a matching `AuthorityFingerprint { generation, published, local }`; it does not require a lineage-based history prefix.
2. The existing first-batch plan and bulk validation remain exact. The DO compares actual authoritative generation and the published full manifest digest before any GET. The Native continuation verifies the original method/target/body/semantic headers, session, nonce, generation witness and plan, re-derives Full selection against current local state, and consumes the verified first prefix once while fetching all remaining batches normally.
3. Only after complete Full materialization succeeds may that same private handler construct `ValidatedFullReceive`. It carries bounded generation, published/local digest, selection/descriptor identity, original request hash, session and nonce bindings; no object payloads, Vec of chunks, cross-request flag or reusable Clone token. Recheck the Full scope, generation, paired authority binding and request identity at receive entry. Invalid token is an error or an explicitly selected charged fallback before receive mutation; never silently cold-read again inside the prepared path.
4. Pass token ownership through the existing receive wrapper. The transaction must retain lineage/advertisement certificate transfer, pending metadata charges, `publication_active`, debt cleanup, quarantine/alternates, strict Git receive and thin completion, exact refs, bounded compaction, import, atomic R14 catalog/publication + sync + retirement, proof semantics and post-publication cache invalidation. The sole skipped step is the first unconditional `cloud_read_view` at current native.rs:1027. None preserves the original step.
5. Materialization belongs in `receive_prepare_seconds`, including all remaining bulk reads. A token can carry a bounded elapsed preparation duration or the wrapper can encompass the authenticated prepared branch; do not begin prepare timing after materialization. Count one logical push, input/output once, no fetch cache miss or receive-response cache insertion. Set push phase before remaining reads; the DO first-batch dispatch must also be push. Increment rehydrate and projection-to-Full counters once.
6. Private receive errors need the ordinary `handle` cleanup: clear invalidated advertisement/lineage and preserve dirty/invalid scope after partial preparation, cleanup, codec/publication or local filesystem failure. Factoring a small common error-cleanup helper is safer than copying a divergent fetch-only error path. After an attempted publication, no hidden gateway receive retry or alternate publication path is permitted.
