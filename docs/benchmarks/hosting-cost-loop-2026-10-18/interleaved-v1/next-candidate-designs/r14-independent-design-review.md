# Independent fused metadata design review

**Disposition: conditionally viable for a clean implementation and early actual-Worker gate; not accepted, implemented, measured, or a stopping result.** A bounded catalog root and its peak can share the existing singleton manifest row. An opt-in fused upload can then replace two normal row writes with one atomic row write while preserving durable publication-before-deletion. This changes the current *separate pre-CAS catalog-sync* contract. It must be specified as atomic coupling, not described as preserving that exact intermediate barrier. I found no necessary violation of the user's freshness, bounded-memory, compressed-storage, or push/fetch requirements. Source review alone cannot establish the SQLite storage guard or actual net saving.

The auditor and I independently discussed the first-write failure mapping and durable representation.

## Atomic coupling is a sufficient narrower guarantee

Current source is explicit: `put()` performs real R2 PUT, catalog/peak SQL and sync; `publishManifest()` then transactionally checks generation, writes manifest and syncs; only a winner calls `retire()`. A failure after real PUT but before the first catalog persistence already leaves an uncertain physical object and requires paid generation-checked physical GC. The current code does not promise that every successful R2 PUT has a durable historical peak when its catalog write itself fails. The new path must not claim to repair that gap.

For the coupled path, real immutable PUT completes first. One synchronous SQL transaction then writes the catalog root and peak together with either the winning next manifest or the unchanged current manifest. The containing service request remains inside the existing `ctx.blockConcurrencyWhile` gate across R2, SQL and sync. No other repository service can observe an intermediate root/manifest mixture. A successful sync precedes a successful publication response and every retirement DELETE. A recovered committed winning manifest therefore has its corresponding root membership and peak in the same row. A transaction failure is a catalog-persistence failure, not a falsely successful CAS. A sync failure is ambiguous and receives no successful upload/CAS response or retirement; Native's existing dirty-recovery rule remains mandatory.

This moves a failure from the old later-CAS-after-catalog category into the existing first-metadata-write category. It is a different persistence protocol, but not a new category of lost-accounting window: both already have a real-PUT/metadata gap. If a requirement literally demands independently durable catalog state before any CAS SQL becomes visible, this candidate is ineligible under that requirement. The user requests correct repository hosting and cost optimization; I found that separate barrier in implementation documentation, not an explicit user prohibition on atomic coupling. The new design must update that documented contract and preserve the stronger useful invariant: no durable winning manifest without a durable catalog/peak witness, and no retirement before its publication sync.

## A concrete bounded durable representation

Use a new nullable private BLOB column on `repository_state`, with an independently versioned envelope, for example `GZIR` + version + member count + safe-u64 peak + safe-u64 applied generation + sorted `(32-byte SHA256 digest, u32 size)` members. With a 22-byte header and 32 members this is at most 1,174 bytes. Sizes retain the existing 0..16 MiB durable-v2 domain; no object bytes enter SQLite. The exact format is an implementation choice, but it must have all these properties:

- The column's non-NULL validated envelope owns the complete root catalog. There is no duplicate `blob_catalog` root or child membership. Do not store a second authoritative copy or add a trigger that secretly writes it.
- Count zero is valid for this envelope and still retains peak/acknowledgment. Reusing current `decodePage()` unchanged is insufficient: GZCP currently rejects empty pages, but deleting the last physical object must not erase the only historical peak witness. NULL means ordinary catalog ownership; empty non-NULL means an inline empty inventory with a durable peak.
- Validate magic, version, exact length, sorted unique digests, count<=32, safe peak/generation, member sizes and any future-ack mismatch. Summed bytes derive from members, rather than independently trusted duplicated totals. An absent row means generation zero, empty manifest and no inline owner; an independent initial PUT may have to create the singleton with the canonical generation-zero manifest.
- Durable decoding is unconditional once the column exists. Registration/capability controls eligibility for the optimization, never whether old persisted bytes are read. Old Native providers, registry loss, reconnect and a no-capability request must remain usable with the new Worker. This is not a promise that an old Worker binary can understand a future durable format; any Worker downgrade needs a deliberate charged demotion/migration before rollback.
- Numeric-invalid or malformed inline state must mark inventory uncertain while leaving manifest reads and generation-checked GC open. Do not throw permanently from the constructor, silently ignore corrupt inline state, or hide a valid high-water witness. GC retains the valid-H plus full physical pre-delete/orphan floor already required for R12/R13; it cannot reconstruct arbitrary history after all witnesses are destroyed.
- Keep at most one bounded decoded root and the existing bounded debt/proof structures; no growing map or object payload cache. Native's 32 MiB joint cache, 256-entry limit, 32 KiB history certificate and fixed proof slot remain unchanged.

Every catalog function needs one ownership abstraction, including constructor/reload aggregate inventory, `catalogLookup`, `missingPageKey`, page writes/deletes, peak preservation, pending-debt loads/flushes, `put`, `retirePages`, authoritative GC/rebuild and metrics comparison. A locally optimized upload that bypasses those other readers is unsafe. Read/metrics/register paths may inspect but must not migrate, acknowledge, flush, repair or certify physical state.

## Exact fused transaction and failure behavior

1. Validate the entire existing GZUP frame, duplicate JSON members, manifest, refs, bounds, immutable SHA256 and matching chunk lengths before mutation, as now. A new exact opt-in capability/header selects the coupled implementation; keep the same endpoint, upload wire bound, response schema and actual receipt requirements. Absent capability uses the existing eager path. Do not broaden a public spoofable header into authority.
2. Resolve only debt that the current protocol can resolve, with actual charged HEADs when a valid proof is unavailable. Arbitrary uncertainty still requires physical GC. Preserve the existing same-key pre-PUT acknowledgment-and-sync barrier. A valid old absence proof must never remain applicable to a resurrected key after its real PUT and a later SQL failure.
3. Determine eligible ownership/size/fallback before issuing physical PUT. Flush unrelated, split, mixed, unacknowledged, invalid or unsupported pending shapes using their current charged barriers. A distinct-key normal same-root path may fold the old survivor acknowledgment into its planned new envelope. The new envelope's applied generation records acknowledgment of *prior* debt, not acknowledgment of retirement belonging to the newly published generation. Advancing it to `next.generation` before physical DELETE would incorrectly certify absence after a crash/partial deletion.
4. Perform exactly one real PUT. Compute the temporary physical total and peak from exact current live totals, handling overwrite/dedup without incrementing object count twice. The peak is the post-PUT/pre-retirement physical high-water mark, even when CAS will be stale.
5. Inside a synchronous transaction, read/check authoritative current generation. Perform one singleton UPSERT/UPDATE that always persists the planned root and peak. If expected generation matches, atomically replace generation and manifest as well; otherwise preserve both current manifest fields and return stale. A stale upload remains a durable orphan or shared key and must not be deleted. A stale fused upload intentionally still has its PUT; the existing *CAS-only* stale/no-retirement paths must remain zero R2.
6. Sync. Only after success update/certify volatile physical totals and return the true CAS result. Enclose transaction/sync failures in the existing uncertainty path. Roll back derived volatile changes or invalidate them; never continue with an apparently exact live inventory after ambiguous persistence.
7. On a synced winning publication, install its debt context and execute the current ordered real retirements, truthful outcomes and final sync/defer rules. A stale result performs no retirement. Proof issuance remains optional after actual receipts have been counted once; it still requires exact successful CAS, all ordered DELETE outcomes, exact upload receipt and known SQL counters. Unknown SQL remains NULL and suppresses proof.

Existing `operation("manifest_cas", ...)` accounting must wrap one logical CAS attempt even though its SQL shares the catalog write. Do not fabricate a separate row write, suppress real cursor rows, count one receipt twice, or manufacture success from the mere existence of the root page. Errors after sending the fused request must never produce scalar PUT/CAS fallback; current Native parsing/dirty-view behavior already requires this.

## Fallback and transition rules

Eligibility should initially be deliberately narrow: validated sole root, <=32 members after insertion, valid totals/debt, bounded combined manifest/root bytes, and no mixed or descendant ownership. Existing valid public PUT, CAS, scalar >256-key retirement and no-PUT publication must remain accepted.

Use an explicit conservative inline manifest-byte cap chosen before implementation measurement; this is a performance eligibility bound, not a new API rejection limit. Preserve the existing 1,500,000-byte metadata limit and all original accepted manifests. If a valid next manifest exceeds the inline cap, chargeably demote the root to the existing catalog layout and clear the inline column in the same transaction, sync as required, then perform the ordinary valid operation. A failed SQL attempt is not a signal to retry PUT or switch publication paths after I/O.

Migration from an existing single normalized root must atomically transfer its complete membership/peak/ack to the singleton and delete the old root. The one-time two-row or greater migration work is paid. Never read all descendants to force a promotion, migrate on reads, or hide work in observer scope. Initial fresh opt-in repositories can create the inline owner directly. An old/no-capability provider may preserve and eagerly update inline ownership, or first demote it durably; it must not accidentally insert a duplicate normalized row. Ordinary CAS-only updates preserve inline state or demote safely, and still perform a real authoritative generation check.

On the 33rd member, a mixed/legacy operation or oversized manifest, a simple safe fallback is a synchronous ownership transaction that writes the old bounded root into `blob_catalog`, clears the inline owner while preserving manifest/high-water state, then syncs before the ordinary eager operation. The existing bounded split implementation handles the insertion afterward. A more efficient direct child split is possible, but must atomically clear inline ownership and write every child with its peak/ack in one transaction and charge all rows; no need to optimize it in the initial candidate. Failure keeps the repository uncertain and recoverable. An inline empty inventory retains its peak until it has been transferred to another durable carrier. GC uses generation-checked physical LIST, preserves full pre-delete peak, and atomically rebuilds exactly one ownership format before sync; observer LIST never performs this conversion.

## Mandatory early actual Worker gate

Before a large implementation or any cloud-VM screen, run a Rust-driven actual workerd/R2/SQLite prototype gate on isolated local state. A fake cursor or expected SQL string is insufficient. Freeze all source/module/test hashes and retain raw real operation receipts.

1. Reproduce the existing 11/13 physical-key, 11-pack, 33-ref shapes with realistic >=4,800-byte manifests; verify final, peak-in-operation where available, post-GC and reopened SQLite size **<=24,821 bytes** (the current 24,576-byte anchor +1%). Test actual generation-zero creation, ordinary PUT+CAS and normal fused upload. The normal eligible fused operation must show one actual SQL written row instead of two, with identical real PUT/DELETE/bytes/peak and no hidden observer writes. Count actual ALTER/migration writes. If an extra SQLite page appears, reject or change the representation before proceeding; do not loosen the guard or replace it with a tiny fixture.
2. Cover the empty inventory peak witness; 32 members; duplicate digest/member; same key used by multiple live pack descriptors; 33rd-member split; very long common prefixes; normalized/v1/v2/mixed and duplicate-owner states; invalid/unsafe/fractional peak/ack/size; maximum valid metadata above the inline cap; and scalar >256 fallback. Every previously valid public operation must remain productive.
3. Fault/restart after real PUT, before/inside/after the single SQL transaction, before/after sync, before first DELETE, during partial DELETE, and after committed but lost/corrupt response. Recover using the same Native where applicable, not test-only GC callbacks. Require winning refs and full strict fsck/archive; exact actual inventory; full pre-delete/orphan peak; no second PUT/CAS on ambiguous outcomes; no deletion on stale CAS; and no false proof or known SQL counts after unknown cursors.
4. Test same-key resurrection with a valid old all-success proof and post-PUT SQL failure, then restart/replay that proof. The durable pre-PUT acknowledgment must prevent the resurrected object from being subtracted as absent. Also test distinct-key survivor folding and stale fused CAS while prior retirement debt exists, without advancing its acknowledgment past actual deletes.
5. Interleave independent valid PUT/CAS/no-PUT/scalar calls with fused operations; repeat after registry loss, old Native registration and DO eviction. Confirm every read/observer stays mutation-free, every current request performs the existing authoritative freshness check, pending debt is paid/reconciled rather than hidden, and final actual receipts and storage remain truthful.

Only after this gate and independent source/fault review should a clean candidate be committed/pushed and get the authorized fresh two-pair four-profile screen. The required final five fresh original-R1/final pairs still remain mandatory. The current R11–R13 run must stay untouched.

## Cost conclusion

The earlier audit's `U+P` SQL floor assumes two separated persistence writes and therefore does not constrain this design. Up to 128 paired catalog/CAS row writes in its earlier illustrative four-profile replay represent $0.128 gross at the frozen 1,000-repetition rate; this is a potential, not a measured saving or net estimate. New DDL, transitions, fallback, routing/constructor reads, proof recovery and SQLite bytes can reduce or erase it and must come from fresh actual receipts. Worker CPU, DO duration, monthly SQLite retention, Native compute and full bill remain unknown. There is enough concrete potential to require testing this candidate if its early gates pass; a global or retained-interface 'no further meaningful optimization' statement would be premature while it is unresolved.
