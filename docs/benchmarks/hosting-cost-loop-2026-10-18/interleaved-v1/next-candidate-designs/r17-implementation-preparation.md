## Registration and bounded session

Advertise a distinct exact capability only when explicitly requested. Its version, subprotocol, session identity, envelope/header/message limits and maximum 16 RPCs per connection are exact validated constants. Missing capability means legacy HTTP; present malformed/duplicate/unsolicited capability fails registration before installing any capability. Reset and close old socket state before registration validation/I/O and on unregister/failure. Preserve all existing witness/first-read/debt proof reset semantics. The socket must not depend on a gateway first-read capability being enabled: warm hosts may still use socket service RPCs.

Upgrade carries the existing secret service token in a header, repo, exact subprotocol and the acknowledged opaque registration session, never a token in a URL. Capture the exact current registration object; bind this socket to that repo and identity. Check identity before dispatch and after awaited operations/before reply. Re-registration/unregister closes a captured older socket. Permit one authorized active socket per registration, with bounded admission and no payload map or pending queue. Registry/isolate loss yields explicit failure; it does not create a lease or a production-wide coordinator.

Native owns one synchronous socket mutex and at most one outstanding RPC. A session rotates after at most 16 completed/dispatched application RPCs, only before the next RPC starts. Count every Upgrade, including failed/reconnect opens, in the actual triggering phase. A startup handshake stays startup; a lazy timed handshake stays timed. No free startup charge is subtracted from a fixed-workload subtotal.

Use strict integer request IDs within the short session, e.g. canonical u32 sequence 1..16, not floating-point u64 IDs. Versioned binary request/response envelopes include exact session/ID, allowlisted method and route, explicit allowed phase, bounded header/proof section and exact body length. Reject trailing bytes, overflow, unknown fields/versions/routes, wrong session, duplicate/out-of-order ID, cross-repo metadata and private-header spoofing before DO work. Response binds the same ID and returns the existing status/body/header semantics. Native applies the existing non-2xx error mapping and typed upload/bulk/CAS decoding; proof is accepted only after full reply identity/shape validation.

No response needs to expose the private DO receipt to Native: the Worker accepts it once through existing `dispatchService` and strips its header before framing. Optional proof issuance follows receipt accounting, so proof/framing/send failure cannot erase physical work. Socket ping/pong/close control frames dispatch no storage operation.

## Exact limits, including fused upload

Preserve 256 bulk keys, 16-MiB bulk payload/chunk, 1,500,000-byte metadata, 32-MiB joint retained budget, 64-MiB incoming push and 128-MiB snapshot limits. Current `MAX_BULK_RESPONSE` is **16,779,276 bytes** (16 MiB + 2,060). Current GZUP `upload_frame` bounds the **whole route body** by that exact value, including its 12-byte header and metadata. A full 16-MiB chunk plus 1.5-MB metadata is not an eligible fused upload; retain its ordinary pre-I/O split/fallback behavior.

Define a small explicit socket envelope/header overhead independent of route bodies, with a checked total below the documented 33,554,432-byte incoming Worker limit. Do not accidentally reuse the larger R15 continuation-frame cap as a route body cap. A maximum metadata-bound test and a full-size chunk test are separate valid boundary cases; an oversized combined GZUP case must reject/fallback before binding I/O. Generic HTTP scalar GET never inherits the socket cap.

On Worker sockets set binary delivery explicitly to ArrayBuffer before accept. A JS busy flag rejects a second application message before DO dispatch and closes on pipelining; it cannot prevent the runtime from fully buffering that incoming message first. One admitted legitimate synchronous sender and no response queue provide only the bounded local control, not a solution for malicious floods or multi-repository isolate concurrency. The per-isolate 128-MB memory/CPU/subrequest behavior and production routing remain limitations of the experiment.
