## Ordinary admission and failure policy

Use an explicit internal read purpose or argument passed through `rebuild_view`, `cloud_read_view`, `fetch_read_view` and the resolver. Only actual ordinary upload-pack/receive-pack materialization admits freshly verified GETs. Planning, initialization `recover()`, observer `/_object-stats`, metrics and maintenance/recovery reconstruction use existing bytes if legitimately selected but cannot populate the slot. Do not infer admission from mutable service phase counters. The default remains a generic production policy, not a benchmark switch.

Both ordinary and prepared fetch/receive paths enter the same resolver. PUT/import/pending publication paths never call admission. Successful push still invalidates response entries and can retain the immutable slot. Failure cleanup may conservatively evict the slot; retaining it is permitted only with complete accounting and joint-budget re-evaluation. Physical deletion is not a cache invalidation requirement for immutable content, but current authenticated selected membership and exact length remain mandatory. A slot is never a durability or generation witness. Native restart starts empty.

Retain current request_error_cleanup, quarantine/thin-pack/ref validation, union-preserving compaction, sync-before-delete, same-key ACK barrier, dirty recovery and physical GC-before-next-PUT behavior. Missing/incomplete/noncached failures remain charged failures. Unknown SQL or lost body receipts remain unknown/incomplete, never zero or inherited. Private failure logical bytes remain accounted once. Existing latest-after-push cold guard in `hosting-bench.rs:1012–1019` is untouched: newly published never-GET-admitted chunks should naturally produce positive actual GET/read bytes.
