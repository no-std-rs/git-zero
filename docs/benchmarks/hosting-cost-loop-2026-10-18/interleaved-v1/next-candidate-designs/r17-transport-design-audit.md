# R17 Worker socket RPC — bounded independent design audit

**Disposition: conditionally viable transport candidate with a material known-request opportunity. No implementation, runtime proof, net score, acceptance, stopping decision or global floor follows.** The retained HTTP service-call interface is not a global optimum: an authenticated Native→Worker WebSocket can avoid repeated inbound Worker requests while still dispatching the same existing DO HTTP call for each logical RPC. The public Git gateway, its fresh authority checks, R15/R16 first-read protocol, R2 read sets and SQLite/durability rules remain unchanged.

Audit performed **2026-10-18**, read/offline plus explicitly requested official-document lookup only. No source edit, dependency install/build, service/probe, CI action or benchmark ran. Source inspected is mutable R15 preparation at `/tmp/git-zero-hosting-gateway-first-read`, based on `5759726b0a4545f6613553e1f2303f303eb65384`; it is not a frozen R17 implementation. The HTTP ratecard remains the existing dated **2026-10-17 `cost.rs`** snapshot; this review verifies the transport billing rule without repricing old results.

## Verified platform rule and its limits

Cloudflare documents that an inbound Worker WebSocket Upgrade is one billed request and routed messages add no Worker request count. Worker subrequests are not additional Worker requests. We retain ordinary DO HTTP requests, so the separate DO WebSocket discount and hibernation rules are not used. CPU is still a metered dimension; no CPU saving is inferred. [Official Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).

The documented incoming Worker WebSocket message limit is **32 MiB / 33,554,432 bytes**; current bounded first-read frames are 18,410,368 bytes. WebSocket connections can disconnect during runtime updates, crashes or shutdowns. The runtime now has compatibility-dependent binary and close behavior; set binary delivery explicitly and handle closure. [Official WebSocket API](https://developers.cloudflare.com/workers/runtime-apis/websockets/).

Workers have a **128 MB per-isolate** memory limit; network wait is distinct from CPU. Current Paid subrequest limits are finite, and connections can be interrupted; a local successful long socket does not prove unbounded lifetime or production capacity. Treat session CPU/subrequest accumulation conservatively until the exact runtime behavior is established, and rotate only at a pre-I/O boundary if needed. [Official platform limits](https://developers.cloudflare.com/workers/platform/limits/).

Miniflare explicitly supports a `WebSocketPair` returned with status 101, so real local Worker controls are feasible; that documentation is not proof that the pinned installed runtime accepts the full production frame sizes. [Official Miniflare WebSockets](https://developers.cloudflare.com/workers/testing/miniflare/core/web-sockets/). The repository pins Wrangler 4.149.0 and compatibility date 2026-10-06. First controls must exercise that exact runtime without experimental large-message flags or raised caps.

## Accounting must represent the new transport honestly

Current `index.js:91–104` increments `worker_requests` and one category on each inbound HTTP fetch. The service route invokes it at `:407–413`. `dispatchService(:347–361)` performs one internal `stub.fetch`, validates/adds its actual receipt and strips its private receipt header. Each DO receipt still requires `do_requests===1`, zero `worker_*` fields, exact operation counts and nullable SQL handling (`:267–319`). These invariants should remain intact.

An Upgrade is a real inbound service request: count it once before authentication success/failure as appropriate to current HTTP counting. **Do not call `workerCount` per WebSocket message.** Instead add unpriced, explicitly named transport diagnostics outside the DO `emptyUsage()`/receipt field set: connection/upgrade attempts and phase, received/dispatched/completed/failed RPC messages, bytes, sequence, close/reconnect reason and known/incomplete outcomes. Logical RPCs remain physically visible even though message handling is not an additional billable inbound Worker request.

`UsageCounters`/`metered_usage` (`accounting.rs:19–35,127–141`) already prices actual `worker_requests` independently of `do_requests`; the evaluator reconciles Worker gateway+service+observer categories (`benchmark_cost.rs:235–272`) and does **not** require Worker count to equal DO count. Thus the unchanged price model can price honest socket invocation counts. This is not permission to relabel existing HTTP callbacks: the new wire transport, handshake and diagnostics must prove that they really occurred. The objective/fixture/rates stay frozen; distinct source/config identities and independent receipt controls establish comparability. Any stricter uninspected orchestration schema must be reviewed before integration rather than bypassed.

Factor the existing authenticated service handler into a transport-neutral internal helper. The socket message calls that helper and then `dispatchService` **directly**; fetching the Worker's own HTTP endpoint or recursively using the top-level HTTP handler would either add real HTTP charges or manufacture counts. Preserve the existing strict request/body validation, capability/header stripping, retirement proof verification/issuance, private trusted header injection, status/body shape and receipt-once order. No new DO schema/protocol, long-lived DO socket or DO duration exemption is assumed. Gateway authority/first-read internal DO dispatches stay where they are.

Observers/registration/unregistration can remain ordinary HTTP. This keeps excluded observer scope explicit and avoids putting metrics/recovery work inside a hidden socket startup phase. Startup socket and ordinary fallback traffic stay visible in complete physical scope. Closing a socket does not unregister the Native codec or destroy durable repository state.

## Bounded protocol, authentication and failure semantics

1. Advertise a distinct exact opt-in socket capability over the existing HTTP registration. Validate present-invalid capability strictly; old/common-Worker clients retain HTTP unchanged. Accept an Upgrade only after exact repo/token/subprotocol/registration-session validation; bind one socket to that repo and registration generation, never accept repo switching from message metadata. No token is put in a logged URL. Local `ws://127.0.0.1` matches current loopback-only HttpServices; deployed `wss://`/TLS hosting is outside this experiment.
2. Socket messages carry a versioned binary envelope with monotonic request ID, allowed method/route, explicit validated phase, bounded canonical headers/proof metadata and body lengths. Reject duplicate/out-of-order IDs, unknown routes, private-header spoofing, malformed/truncated/oversized envelopes before binding I/O. Restrict routes to existing supported service RPCs. All underlying 16 MiB chunk/bulk, 1.5-MB metadata, retirement/ref/request/snapshot and response limits remain. A response carries the same request ID, HTTP-equivalent status, bounded response headers/proof and body; preserve existing typed JSON/bulk decoders.
3. One Native socket mutex owns **one outstanding RPC**, with no request queue, pending-map, retained frame history or cached object payload. Worker rejects a second concurrent message before DO dispatch rather than queueing blob bodies. Mutable registration/session replacement is checked before dispatch and before returning a reply; unregister closes the captured old socket. Existing per-DO gate still serializes storage work. No freshness check is replaced by registration lifetime or a lease.
4. Reconnect only by an explicit authenticated handshake **before beginning the next RPC's I/O**, with separately charged Upgrade. An initial unsupported handshake can choose HTTP before any storage mutation. Once any RPC frame might have reached the Worker, send/read failure, timeout, close, missing/malformed response or lost acknowledgment is ambiguous: return the existing error, preserve actual Worker receipts/incompleteness and Native dirty recovery; **never resend the RPC or fall back to HTTP**. A new session must not replay an uncertain write. A ping/ready exchange can establish idle liveness but cannot prove a later write had no side effects.
5. Worker accepts/adds each DO receipt exactly once before response framing/proof/send can fail. Native validates response ID/size/integrity and existing typed response before accepting any proof. No application acknowledgment re-adds a receipt. If the Worker has already recorded a receipt and the reply is lost, costs remain recorded; if DO dispatch/receipt is ambiguous, accounting remains incomplete rather than zero. A runtime aggregate epoch reset is still an invalid trace, not repaired by reconnecting or relabeling counters.
6. Registry/isolate loss and older-Native reconnect remain productive through supported HTTP/startup recovery. A captured socket session must not silently continue under unrelated newer registry keys. The new socket may keep its Worker isolate resident longer; do not assume public requests always route to that same isolate in production or claim that the existing loopback registry/accounting is a production-wide coordinator.

## Compatibility and memory falsification

The general HTTP service client allows **up to 128 MiB** scalar responses and supports legacy chunks too large for the bulk route (`cloudflare.rs:call`, `validate_bulk_chunks`, `bulk_batch_len`). A single 32-MiB-limited socket message cannot transparently replace every generic scalar read. **Keep scalar GET on HTTP unless its response bound is already known before I/O to fit.** No HEAD probe may be introduced merely to choose a transport, and no oversized response may trigger a retry after a possibly mutating request. Unknown-size/unsupported legacy routes stay HTTP from the start. The measured R13 normal bulk/upload cohort does not require those oversized scalar GETs, so this compatibility fallback does not erase the identified opportunity.

Cargo.toml/lock currently contain serde, hashes/HMAC and std networking; **no WebSocket, Tokio, TLS, masking or HTTP-handshake client crate is locked**. A blocking `tungstenite` client is compatible in shape with `HttpServices`' synchronous TcpStream calls: its official API offers custom-header blocking handshakes and configurable message/frame/write/read buffering. It would be a new pinned dependency/lockfile/MSRV audit, not an already available facility. Prefer a reviewed implementation over inventing an incomplete RFC6455 client. [Tungstenite client API](https://docs.rs/tungstenite/latest/tungstenite/client/index.html), [buffer/size configuration](https://docs.rs/tungstenite/latest/tungstenite/protocol/struct.WebSocketConfig.html).

Do not trust defaults: require fresh random client masks, strict 101/Upgrade/Connection/accept/subprotocol checks, bounded header parsing, text/RSV/opcode/control/fragmentation validation, max frame **and reassembled message** bounds, timeouts and no compression expansion. Ping/pong/close controls may interleave without becoming storage RPCs. Source has SHA1 already but not a complete handshake/masking/framing implementation. Keep the crate local to the std host example; no async runtime is needed merely for this design.

The socket's retained read/write buffers, key/session/sequence/mutex structures must count inside the existing **32 MiB joint retained budget** and trim response cache through the existing policy. One logical outstanding RPC does not itself prove the memory bound: a library can retain an 18-MiB outgoing buffer and another incoming buffer after returning. Configure small streaming buffers, transfer/drop message ownership promptly and demonstrate retained capacities after maximum messages/errors; do not retain both full request and response frames as hidden cache. Existing request-local pack buffers and Worker framing copies are not a claim of 32-MiB total process RSS.

Worker WebSocket `send()` is not a promise of peer consumption. A strict request/reply peer must consume the whole response before its next RPC; close on pipelining/flooding, do not accumulate response buffers. Across sockets, bounded registration count alone does not bound simultaneous 18-MiB frames below 128 MB. Use explicit bounded admission/in-flight bytes with pre-I/O HTTP fallback for unsupported socket capacity, without rejecting an otherwise valid generic HTTP API. No unbounded payload queue or session map is added. Actual memory/latency and same-isolate concurrency controls are mandatory; CPU-budget/reset semantics and production capacity remain unproven by local emulation.

## Mandatory first controls before an implementation is considered viable

Use the existing Rust-driven real workerd harness only, at frozen new source, without new MJS execution runners or cap overrides:

- Authenticate Upgrade and prove **one actual counted Worker request**, then two or more socket RPCs produce zero further Worker requests but exactly one valid DO HTTP receipt each, correct per-message phase and exact unchanged R2/SQL bytes/attempts. Compare ordinary HTTP controls; retain unpriced socket message diagnostics so counters are independently reconcilable.
- Exercise full 16-MiB PUT and read/bulk frames, 1.5-MB metadata boundaries and the proposed maximum wrapper, plus message/fragment/length/control-frame rejection. Verify the pinned workerd size behavior without an experimental larger-message flag. Generic >32-MiB scalar reads choose HTTP before I/O and remain valid.
- Run real Git small/large/thin push, immediate post-retirement historical/latest reads, existing first-read fallback and strict fsck/archive. Require identical manifests, physical operations, peak/storage, SQLite 24,576-byte normal shape, all caps and joint retained allocations. No new object cache or stale gateway authority is allowed.
- Fault disconnects before send, mid-header/body, after real PUT, after coupled CAS/sync/DELETE and before/after reply. Verify zero automatic resend, exact failure receipts or explicit incompleteness, same-key/proof barriers, dirty generation-checked recovery, lost committed reply handling and productive later explicit reconnect.
- Check registration/key rotation, old Native/common Worker compatibility, duplicate IDs/cross-repo/private-header spoofing, close/ping/flood behavior, idle/runtime restart and aggregate epochs, observers over HTTP, session-open/close phase accounting, sustained RPC sequence, allocation retention and no payload queues.

Only after independent source/fault/accounting review should clean pushed code enter the unchanged fresh four-profile screen. Replace 429 with actual preceding traces, include every Upgrade/reconnect/fallback and unknown dimension, and retain the existing latency/resource guards. Current HTTP request budgets and per-callback SQL choices do not justify stopping while this interface change remains a credible unmeasured candidate. **STOP READY; no implementation or benchmark authorization is implied.**
