# Initial large snapshot: conditional physical-container design

**One streamed physical PUT is plausible, but no implementation candidate is qualified.** A separate HTTP upload protocol could store the initial 34,207,816 B snapshot once and retain its existing three logical chunks. The present common Worker, GZUP upload, socket protocol, catalog encodings and retirement proof do not support this. If compatibility means an unchanged common Worker must operate on the new storage, reject this candidate: its GC cannot interpret the required mapping. A new Worker format boundary is indispensable.

## Concrete proposed upload sequence

Scope eligibility to an authoritative empty generation-zero repository, one new bundled pack, no previous packs/debt, `16 MiB < pack+index <= 64 MiB`, bounded metadata, and an explicitly negotiated `initial_container_v1` capability. Do not switch formats for subsequent pushes or coalesce published objects. Failure of an eligibility/capability check before dispatch uses the existing route; a dispatched error never falls back.

1. Negotiate in the existing registration exchange, with an exact version/body/metadata/range limit and private session authentication key. No probe or extra authority request. Native first computes the whole physical SHA-256 and the original ordered logical digests over the virtual pack-then-index concatenation. Keep the logical partitions **16,777,216 / 16,777,216 / 653,384 B** and existing `Chunk {key,len}` manifest, mask, selection and cache identities.
2. Use a **new HTTP-only callback** `POST /_services/manifest/initial-container`, bypassing socket framing before dispatch. Put strict canonical metadata in a bounded header: at most 4,096 decoded bytes / 5,464 base64 bytes, below the current 8,192 B line limit. Bind repository, registration session/nonce, expected generation, complete next manifest, physical key/total, ordered logical key/offset/length tuples and mapping digest with a request MAC. Oversized metadata is ineligible before mutation. The binary body contains only the 34,207,816 original bytes; Native writes the already owned pack and index slices sequentially, without a concatenating Vec or larger socket message. Require exact Content-Length, no transfer/content encoding, no redirects/retries. Both body and the entire proposed bounded header-plus-body are below 64 MiB in this case.
3. The Worker authenticates/bounds metadata before forwarding one stream in **one counted Worker request and one DO dispatch**. The DO retains existing serialization, current-generation authority and catalog-certainty checks. It rejects a nonempty/stale repository before PUT; cancellation/draining must finish before returning, so an active upload cannot strand the gate. Once PUT starts, all errors are ambiguous. Do not call the existing `bytes()` collector for this route.
4. The DO starts exactly **one** `BLOBS.put(repo/physical_key, fixed_length_stream, {sha256: physical_digest})`. A backpressured pump checks exact total and logical boundaries while updating one streaming logical SHA at a time. Await digest writes and downstream writes; do not create an independently advancing tee, buffer the container, or silently use multipart. Verify all logical digests before publication. Await successful R2 completion and exact returned size/checksum. No HEAD, LIST, copy, temporary R2 object, create/part/complete or separate manifest PUT belongs to the successful path.
5. In one SQL transaction, compare expected generation again and durably own **one physical catalog entry of 34,207,816 B**, a bounded three-range map, peak witness and the winning next manifest. Sync before acknowledging CAS or any later DELETE. A lost/stale publication keeps a durable orphan catalog entry; it never authorizes client-side deletion. A small exact receipt binds physical key/size, mapping digest, publication result and truthful usage. Missing/malformed receipt leaves the result ambiguous and accounting incomplete.

The proposed route changes the **internal physical upload format**. It does not raise the existing 64 MiB Git receive limit or 128 MiB snapshot limit, and cannot be described as passing through the current 16 MiB upload/message contract unchanged.

## Why one PUT is credible, and what remains unproved

Installed primary Miniflare implementations have separate single-PUT and multipart methods, streaming checksum validation and ranged GETs (`bucket.worker.js`, recent cache lines 329–436, 943–994, 1101–1152). Official [Workers R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) documents stream PUT, SHA-256 verification, range options and returned range metadata. [R2 limits](https://developers.cloudflare.com/r2/platform/limits/) allow a single-part upload above this size. [FixedLengthStream](https://developers.cloudflare.com/workers/runtime-apis/streams/transformstream/) supplies an exact known length; [DigestStream](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/) avoids retaining the input solely for hashing. This is API evidence, not a runtime or allocation proof.

The inspected installations are Wrangler 4.116.0 and 4.151.0, whereas R20 locks 4.149.0. No exact pinned execution occurred. Exact-runtime stream acceptance, BYOB support on the forwarded request, provider queues, cancellation and gate behavior remain falsification gates. A full-body `arrayBuffer()` implementation is not an acceptable substitute for the proposed bounded pump.

Multipart is rejected: with the existing 16 MiB part limit it requires create + three parts + complete = **five Class A operations**, versus the existing three. Even a single-part multipart sequence needs three and removes no Class A. Charge retries/list-parts/recovery too. Contrary to treating every API name as Class A, current official [R2 pricing](https://developers.cloudflare.com/r2/pricing/) lists AbortMultipartUpload as R2-free; its actual Worker/DO/SQL requests and incomplete-part storage/lifetime still count. Never hide abort work or incomplete uploads behind that free R2 operation.

## Logical authentication and physical reachability

The least invasive client design is a **Worker-owned storage index**, not new public Chunk fields: store a canonical versioned map in the same repository-state row, bound to the upload receipt and atomically installed with the initial CAS. It binds full physical SHA/key/total and ordered logical SHA/key/offset/length; enforce positive lengths <=16 MiB, checked addition, exact nonoverlapping contiguous coverage, fixed order, no conflicting aliases and no mutable reassignment of a live logical key. Retain the mapping as durable storage metadata across Native/DO restarts, independently of ephemeral registration. Treat invalid/unknown mappings as uncertainty: no reads admitted as verified and no mutation/GC until authoritative reconciliation. The existing logical SHA check authenticates every returned payload independently of the opaque physical translation; no assertion that the old manifest fingerprint authenticates new physical metadata is made.

Both bulk/first-authority reads and scalar legacy GET must resolve mapped logical keys and issue **one exact ranged R2 GET per logical read**, without a preliminary HEAD. Validate physical object total, returned offset/length, bounded consumed length and original logical SHA before cache admission/materialization. A full-body or ignored-range response must be canceled, billed as actually attempted/consumed and rejected, never cached or sliced after a 34 MiB download. Preserve <=16 MiB logical payload and existing aggregate response framing limits, GET order, repeated-key semantics and unknown-consumption receipts. Do not merge neighboring ranges or credit fewer Class B calls. Native receives privately owned logical Vecs; no 16 MiB slice may retain a 34 MiB backing allocation.

Let `L` be all logically live manifest keys. Physical reachability is:

`P(L) = ordinary live object keys UNION {container_key if ANY mapped logical key is in L}`.

Catalog/storage accounting uses the distinct physical inventory, not the sum of logical aliases: one full container size once, plus all ordinary objects and orphans. Maintain the immutable range table while any member, retirement debt or unresolved physical operation requires it. Logical deletion needs a durable tombstone/alias state; it must not make another live range unreadable. Delete the physical container only after an authoritative CAS leaves **no** live mapped member and its durable debt/peak witness is synced. Do not rewrite survivors in the ordinary design. A logical retirement receipt must not fabricate three R2 DELETE attempts for one physical deletion. The present deferred proof requires exactly one successful physical DELETE per logical debt key (`retirement-proof.js:32–57`); it needs a distinct reviewed physical-debt proof, or proof suppression with all actual recovery HEADs charged. Current HEAD reconciliation also needs mapping/size translation.

First-empty-repo scope avoids cross-push copy-on-write. It does **not** prevent later partial retirement: retaining only the tail still retains 34,207,816 physical bytes, leaving **33,554,432 B** unreachable slack. Keeping it is correct but potentially far above a 1% live-storage guard. Evacuating survivors adds writes and coexistence peak and is not free. The audit shows full root chunks in final benchmark manifests; that is not a universal lifetime proof. Before any candidate claim, verify every actual intermediate manifest/GC inventory in each profile. Any profile with >1% read/write/live/peak/client/HTTP amplification rejects the candidate. No general workload amplification guarantee is established.

Before orphan/retired deletion, price and preserve the maximum distinct physical bytes actually present, including unacknowledged PUTs, duplicates and failed DELETE survivors. A PUT-success/SQL-crash window can leave up to the entire 34,207,816 B orphan until paid generation-checked recovery; no short lifetime is promised. A future new snapshot may coexist with it. Recovery must LIST/reconcile the physical namespace, derive `P(L)` from current authority plus durable map, checkpoint/sync the pre-delete physical peak, then delete and rebuild the physical catalog. Same-Native recovery and fresh Native/DO restart use the same rule. No ambiguous upload resend is allowed to repair a missing map/receipt.

## Owners, compatibility and source seams

Native's pack/input Vec or borrowed receive body and index already exist at `native.rs:1407–1423`; streaming must borrow them. New persistent capability/session state and any planning metadata belong inside the existing **32 MiB / 256 entry joint owner budget**, with **pool32 and socket reservation262144** unchanged. Count String/Vec capacities, map/control copies, pending proof/lineage, header encoding and reply owners. The DO map is a separately owned bounded three-tuple structure; Worker header parsing, DO parsing and stream queues can coexist and must be measured. Proposed pump scratch is <=64 KiB plus digest states; exact runtime queues, SDK buffers and allocator capacity are unproved. No client-memory reduction is credited merely because staged 16 MiB scratch disappears. Worker CPU, DO duration, monthly SQLite storage and Native compute remain unknown.

They need explicitly versioned larger-member encodings/reopen/migration; relabeling a container as three entries hides physical reachability and is rejected. This changes the common Worker tree; it is not Native-only or an additive fit-response change.
