# Fresh schema / first inline owner: independent design audit

**Decision: retain as a narrow conditional candidate, with a small first gate before broader implementation or screening.** Same-column final CREATEs plus a first standalone PUT that creates its real inline owner can remove **16 timed SQL written rows across four profiles, $0.016 per 1,000 repetitions**. This is a source-supported hypothesis, not a measured saving or source approval. The initial proposal needs two refinements: no existence probe is necessary, and physical-empty eligibility cannot survive a restart merely because SQL is empty. Losing that eligibility must take an honestly paid fallback.

This audit was read-only: no worktree edit, implementation, runtime, build, test, benchmark, CI, push, deployment, MJS runner or delegate. Only the report, offline file calculator and data JSON under `/tmp` were written. **Root GO and independent approval of the exact R19 source are required before any future code.** The mutable R19 worktree was not read. R18's exact source-only approval at `f1ba8f548507dca1e5ab78e5c5d20d8360ecee21` does not measure its ledger or authorize this next candidate.

## Source path and necessary production interface

The R17 constructor (`cloudflare/src/index.js:582`) executes three legacy CREATE statements and `reloadCatalog()` before `fetch()` can see the first request. Native startup (`src/native.rs:713`) loads the manifest and performs generation-checked physical GC before ordinary registration (`src/bin/repository-host.rs:95`). Registration cannot retrospectively select a fresh schema. An always-modern constructor would change old Native under the common Worker; a cosmetic Native edit would not provide meaningful attribution.

Use a bounded authenticated HTTP request, for example `POST /_services/manifest/bootstrap` with exactly `{version:1, initial_columns:"inline-v1", early_inline_owner:1}`. This is the candidate Native's **one initial manifest load**, replacing its existing GET, not an additional startup exchange. Keep the request bound at 1,024 bytes, with strict duplicate/unknown/type/version checks before DO dispatch. The Worker must authenticate the local token before admitting this route, strip caller internal headers, and reconstruct its own private bootstrap marker. Public Git headers, a phase label, benchmark label or environment fixture flag must never choose the schema. Bootstrap need not be an eligible socket route; leave R17's socket capability, bounded routes and 16-RPC session unchanged.

The typed reply must contain an exact version, repository, authoritative manifest, **actual durable column flags**, and exact early-owner capability `{version:1,members:32,manifest_bytes:8192}`. It must not assert physical emptiness, that an existing table was newly created, or that later migration is free. Candidate Native validates the strict envelope, repository, bounds, manifest and capability before use; the returned manifest supplies initial recovery without a second `state.load()`. It then performs the same actual recovery/materialization/GC. Later error recovery and ordinary loads stay ordinary authoritative manifest loads. A missing or invalid acknowledgment fails; a silent second ordinary GET or fallback retry would add paid work and spoil the intended comparison. Older Workers can report unsupported/error with their actual paid receipts retained; rollback to one is an explicit compatibility boundary, not a free negotiation probe.

Native must retain the validated early-owner capability and request/validate it through the existing registration exchange, including inline/deferred/upload-retire dependencies. The common Worker forwards an early-owner internal marker only for that exact active registration. Old Native does not send it. Registration loss/replacement clears optional capability/session state; it never clears durable ownership, certainty or peak. No extra DO query is needed at registration. This actual Native manifest/capability consumption, and its resulting ordinary PUT semantics, provide substantive attribution.

## Safe lazy initialization with no schema-existence probe

Move SQL initialization out of the constructor into the existing serialized DO first-request gate. Constructors initialize accounting/state only. Within `blockConcurrencyWhile`, establish the request phase and one DO-request count, validate the trusted first-request choice, then initialize and handle it. Lazy-init failure must still yield one correctly charged receipt when possible; moving work before the old `handle()` request increment cannot produce zero-DO receipts. Preserve one disjoint per-RPC delta, first-request phase attribution, receipt-once aggregation and sticky NULL/unknown accounting on failed cursors.

A valid candidate bootstrap chooses the same three CREATE statements with final columns: `repository_state` includes nullable `catalog_root`; `blob_catalog` includes `peak_bytes INTEGER NOT NULL DEFAULT 0` and nullable `entries`; `high_water` is unchanged. No eager singleton, root, metadata seed, fourth table, trigger, schema-version row or ALTER belongs in empty startup. The three statements must still charge exactly six written rows in real workerd. Creating final schema directly is reduced work; performing the same three paid ALTERs earlier is rejected.

**Do not query sqlite_master first.** `CREATE TABLE IF NOT EXISTS` with final columns creates absent tables and leaves existing tables alone. The existing `reloadCatalog()` PRAGMAs already reveal the actual columns for a truthful reply. Existing legacy tables therefore keep the ordinary paid migrations at mutation; do not guess newness from `databaseSize`, a missing singleton or an empty manifest. No table is reset/dropped/recreated. Existing partial/legacy/page/inline stores must reopen by durable format; a partial CREATE failure cannot grant modern eligibility or erase uncertainty.

For the same final Worker, old Native's first manifest GET selects the **exact legacy three-CREATE/reload sequence**. First valid request wins initialization while the gate is held. An authenticated metrics request arriving first selects ordinary legacy initialization; the later candidate must report and pay that outcome. It must not reset the store to recover a benchmark target. `/health` does not initialize the DO. Reject malformed or unauthenticated bootstrap at the Worker before DO/schema work; arbitrary old methods/unknown routes retain ordinary legacy handling. Registration alone does not initialize a DO. Test old/candidate/stats concurrency explicitly; no await outside the gate may let two initializers race.

Final columns likely add three returned rows to existing PRAGMA scans per fresh startup, or 12 rows across four profiles. At the frozen rate that would cost **$0.000012 per 1,000 whole-trace replays**, if actual workerd counts them that way. This is conditional, not a cursor measurement. Startup is outside the fixed objective, so report this whole-trace overhead separately rather than adding it to or hiding it in the fixed score. Every actual reopen/probe/read in timed phases must still be counted normally.

## First standalone upload creates the actual owner

The 16 MiB initial publication already has one final coupled upload/CAS; final columns can remove its three ALTERs without a separate owner seed. For 64 MiB, two ordinary standalone uploads precede the coupled final upload. Merely creating final schema would still write a root catalog row, later promote it, and delete it. Both components are needed for the 1/3-written-row target.

Use a narrow eligibility bit produced by **successful actual generation-checked startup GC**, while the same DO instance remains authoritative: final columns exist, state is absent, authoritative manifest is generation zero/empty, no retained catalog member exists, catalog certainty is valid, and no pending debt or mutation ambiguity exists. GC must complete its ordinary sync and preserve the full observed physical peak before setting eligibility. This is an optimization over an actual reconciled empty owner, not an R2-empty inference from absent SQL. Do not create a persistent eligibility row or pay for a certificate seed. Candidate Native waits for this ordinary recovery to succeed before registration/publication.

On the first eligible standalone PUT, validate immutable key, SHA256, length and capability dependencies before physical mutation. An empty inline root may exist transiently in memory, but its first durable write is **after the required successful R2 PUT**: one paid repository-state insert/upsert containing generation-zero empty manifest and the real chunk member, applied generation zero, and `max(existing durable/volatile peak, new live bytes)`. Sync before acknowledging upload. Do not call an UPDATE-only helper against a missing singleton: that can silently write zero rows and lose the catalog. Do not overwrite a concurrently existing generation/manifest; retain the serialized transaction/check semantics and make unexpected state fall back or fail safely.

The second standalone PUT updates that owner once and syncs; final PUT+CAS keeps R14's single atomic catalog/manifest upsert. Thus the expected successful initial push is one write for 16 MiB and three for 64 MiB, with the same one/three real PUTs and one attempted/winning CAS. **The optimized 64 MiB trace must contain no normalized root insertion, transfer or promotion DELETE.** Each later push remains one written row; totals become 32/34. No logical payload, chunk, acknowledgment, sync or publication is moved outside the timer.

Eligibility is invalidated by any possible mutation, failed SQL/PUT/sync, inconsistent observer, reload or DO restart. A restart cannot reconstruct an empty-inventory witness from the modern schema. It takes the existing paid normalized/promotion fallback unless another ordinary required GC genuinely establishes eligibility. No extra recovery LIST/RPC is added just to force this saving. Losing eligibility may leave only the $0.012 schema benefit; that alone is under 1% at the illustrated denominators. The first gate and later screen must retain that loss honestly. If the design requires guaranteed savings through arbitrary idle eviction, a separately reviewed piggyback authority proof would be needed; no free persistent marker is assumed here.

## Peak, durability and compatibility conditions

An empty SQL store may have an R2 bucket full of untracked orphans. Modern startup's existing GC must LIST every page, include all pre-delete physical bytes in peak, checkpoint and sync its high-water witness before deleting any orphan, then retain that peak in the first new owner. This exception can legitimately add paid recovery writes: do not insist an orphan recovery has the empty-R2 six-write baseline, reset H to zero, or label that work an observer operation. Metrics may observe and increase H or mark uncertainty; they never initialize/promote an owner, certify empty recovery, or repair a dirty catalog with SQL writes.

Missing/lost PUT, post-PUT cursor, transaction, sync, CAS or reply must retain actual attempts/bytes and make the catalog/Native dirty. A subsequent mutation on the same Native requires ordinary manifest recovery plus actual generation-checked physical reconciliation. Do not automatically replay an ambiguous mutation. GC reloads durable ownership before rebuilding it; an in-memory provisional root must not survive as an owner after an unsuccessful insert. Unknown cursor rows stay NULL; missing service receipts leave accounting incomplete and never become zero or synthetic successful receipts. Sync of coupled winning manifest/catalog still precedes every retirement DELETE.

Existing non-NULL owners, including zero-member owners preserving high-water H, reopen by durable format even with old Native, no registration or a lost Worker registry. A new registration is not a storage reset. Existing normalized debt, legacy larger chunk descriptions, external generation, stale expected generation, unsafe/future acknowledgments, invalid/overlapping catalog data and high-water corruption retain existing fail/GC behavior. Keep 32 members, 8,192-byte inline manifest, 16 MiB chunk, snapshot/retirement/bulk bounds and current demotion rules. Unsupported shape demotes safely and pays its actual work; read-only authority never promotes. The additional Native acknowledgment/flags must be bounded and charged within the unchanged cache/control budget. Retain R18/R19's current digest verification, current membership/authority, no PUT admission, joint 32 MiB/256-entry accounting, request cleanup and caps.

## Dollar margin: strict tails matter

Frozen rate source is `src/cost.rs`, verified **2026-10-17**, SHA256 `fd27fe75cb9a87117151eb779ff561ddf8a02b550e10f5d7b1ddd4b2181b6756`; no present-day price claim is made. At 1,000 repetitions, one extra trace SQL read costs $0.000001, SQL write $0.001, Worker+DO callback $0.00045, ClassB $0.00036 and ClassA $0.0045. No CPU/elapsed estimate or new billing discount is used.

The fresh actual known scores are R15 $1.64123743618, R16 $1.61963943618 and R17 **$1.49963343618**. R17's conservative min/max are $1.49963143618 / $1.49963543618. The raw comparisons remain inconclusive and plateau-ineligible; R17 is only the root's provisional known-cost anchor. A mean-only $0.0010036656382 margin slightly overstates the strict gate. The correct conditional headroom is `0.99 * preceding_min - (preceding_max - 0.016)`:

| Preceding denominator | Mean known dollars | Gross $0.016 percentage | Strict added-cost headroom |
| --- | ---: | ---: | ---: |
| Observed R17 anchor | $1.49963343618 | 1.06693% | **$0.0009996856382** |
| R17 less conditional ONE $0.05616 | $1.44347343618 | 1.10844% | $0.0015612856382 |
| R17 less conditional ONE and additional MULTI $0.17784 | $1.32179343618 | 1.21048% | $0.0027780856382 |

The latter two rows assume the prior dollar savings occur identically in every trial, unchanged tails and no other cost change. They are **not observed combined scores**. A fresh post-R19 denominator must replace them.

At the R17-only strict margin, even one additional timed SQL written row across the four-profile replay costs $0.001 and misses the threshold. Four extra bootstrap Worker+DO callbacks cost $0.0018 and fail both the R17 and conditional ONE cases. Even where that arithmetic might pass after MULTI, adding those calls still violates this proposal's explicit two-call startup gate. A new ClassA operation is too expensive for all three margins. Before any other overhead, strict margins allow at most 999 / 1,561 / 2,778 additional aggregate fixed read rows. These are budget arithmetic ceilings, not reasons to add probes or new request work. Measure actual read savings/overhead and all phases.

## First required gate and rejection criteria

After root GO and exact R19 approval, freeze old/candidate Native commits and binaries, one common final Worker/config/lock/rates, Rust driver and fresh namespaces. Use the **real production workerd service bridge**, not a fixture implementation of bootstrap. Rust owns fixture creation, orchestration and assertions. A bounded test-only cursor/R2 recorder may expose actual production binding calls; it must not seed schema, catalog, owner or protocol capability and its own reads/calls must remain separate and visible.

1. Start old and candidate fresh 16 MiB and 64 MiB, cold and warm, with no first observer or initialization probe. Capture initial request, all CREATE/ALTER/INSERT/UPDATE/DELETE cursors and rows, every actual service/R2 attempt, receipts/epochs and raw acknowledgments. Old Native under the same Worker must retain legacy startup and 4/8 first-push writes. Candidate must show exactly **2 startup Worker/2 DO calls, 1 LIST, 6 written rows**, no empty-startup ALTER, and no singleton seed.
2. Execute the unchanged production first push, all 31 later pushes and first real reads. Require actual **1/3 first written rows, 32/34 fixed totals**, one/three PUTs, one attempted/winning CAS, unchanged bytes/refs/manifests/strict fsck, and no 64 MiB root promotion. Record full first-push/current/final physical objects/bytes and pre-delete peak, schema/cursor rows, first-read receipt and current SQLite bytes; preserve the 20,480-byte fresh startup/first-push SQLite footprint, 24,576-byte final guard and existing transfer/cache/storage limits. First cold latest reads need natural real new-data GETs; warm/startup/PUT/stats cannot admit cache chunks. Price actual deltas; never force GETs to meet a guard.
3. Exercise legacy, peak, v1/v2 page and inline stores; absence/presence of singleton; paid migration; old Native reopening a new owner after registry loss; candidate ordinary recovery; 16 MiB chunk and inline/member/manifest boundaries; zero-member high-water owner and demotion. Read-only requests, including early first reads, must do no SQL promotion/write or R2 mutation.
4. Exercise wrong token, malformed/duplicate/unknown bootstrap, old first GET, authenticated stats first and simultaneous old/candidate/stats requests. Require one serialized, truthful schema choice; no overwrite/reset/hidden retry. Repeated bootstrap may acknowledge existing columns but cannot resurrect physical-empty eligibility or fabricate a free table creation. Include a store with no SQL tables but real R2 orphans and high-water observations, verifying physical peak is synced before DELETE and inherited by any later owner.
5. Fault R2 PUT before/after side effect, first owner cursor/transaction, sync before/after durability, final CAS, retirement and missing/invalid receipts. Check exactly one logical attempt, sticky SQL NULL/incomplete accounting, unchanged sync-before-DELETE and actual GC before following mutation on the same Native. Force DO loss between startup GC and first standalone PUT: either a legitimately supported witness survives without extra work, or eligibility is lost and the actual paid fallback is recorded. Correct fallback is required; its cost is not credited as the optimized target.

**Reject this narrow target immediately** if the basic fresh production pair needs an extra request, empty owner seed, increased startup written rows, moved ALTERs, hidden observer/preload work, an added SQLite schema page, untruthful existing-store acknowledgment, 64 MiB promotion, missing receipt, invented SQL zero, read-only mutation, larger caps or changed physical bytes/peak. Report an honest first-gate failure if 1/3 and 32/34 are not actually observed. Keep all failures and ambiguous attempts. Only after independent gate/source review should a fresh matching all-profile screen be considered.

No unconditional positive net lower bound, acceptance, latency win, plateau, global floor or stopping conclusion follows. Worker CPU, DO duration, monthly SQLite retention and Native compute remain unknown.
