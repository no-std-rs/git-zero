## R16 cohort and priced opportunity

The actual R13 schedule contains 24 small pushes in **each** profile/sample. In both cold profiles every one performs one cold rehydration, has positive Full snapshot GETs/bytes and a nonempty first bulk callback. Thus there are **48 structurally eligible cold small-push callbacks per four-profile replay**, reproduced in both samples. Reported small-push wire bytes are 712–719 (16 MiB) and 715–722 (64 MiB), below the existing 128 KiB original-body budget. First batches contain 51 total GETs across the 24 operations in 16 cold and 24 across 64 cold; these GETs must remain real, with the same bytes. Warm profiles have no such read opportunity.

The complete original HTTP bodies/headers are not archived, so 48 is a proved **structural cohort**, not retrospective proof of every exact future MIME/header/pkt-line classifier branch. Fresh production-Git controls must establish those branches without fixture-specific handling.

If R16 combines each existing authority call and first Full bulk read into the same internal DO dispatch, it removes one existing Worker service request and one DO request per successful cohort operation: **48 × (`.0003 + .00015`) = $0.0216 gross**. It introduces no new DDL, persistent representation, normal R2 operation/byte, object cache, spool or session map. At an illustrative post-R15 score around `$1.64`, a 1% net target allows only about `$0.0052` additional known overhead; use the actual preceding score when measured. No R14/R15/R16 net price or percentage is asserted here. New crypto/Native work is unknown compute, and extra loopback stages require actual latency measurement.

## Source falsification and required narrow integration

Current R15 source at `/tmp/git-zero-hosting-gateway-first-read` is mutable preparation atop `5759726b0a4545f6613553e1f2303f303eb65384`, not accepted R16 code. Its `native.rs:1027` calls `self.cloud_read_view()` **unconditionally** at receive transaction entry. `cloud_read_view():759–766` always reconstructs in cold mode even when the existing scope is Full. Consequently, simply pre-materializing Full then calling ordinary receive would read the snapshot twice. This material issue was immediately sent to root; root expressly adopted a narrow typed per-call preparation argument.

Use `Option<ValidatedFullReceive>` passed by value into receive/receive_transaction. Construct it **only** inside the authenticated same continuation after the complete exact Full snapshot has been materialized and verified: generation, paired published/local manifest digests, all ordered descriptors, request hash/nonce/session and current Full scope match. It contains bounded metadata only and is consumed exactly once on the stack. At receive entry revalidate scope, current generation and complete binding; a changed/invalid token is an error or an explicitly selected, fully charged fallback before entering the prepared path. Do not install a global pending/prepared flag, persist object bytes across requests, replace ordinary cold policy with broad `require_full_view()`, or silently reread after validation failure. **Ordinary receive with None keeps its unconditional cold reconstruction unchanged.**

The existing R15 matched continuation (`native.rs:1650–1789`) is fetch-specific: it sets fetch phase/cache-miss metrics, calls `native_read`, and inserts a read response in cache. R16 must branch into the normal receive transaction, not reuse that fetch tail. Count the logical request and input/output once, classify service phase as **push** before remaining reads, preserve prepare/codec/publication timings, `publication_active`, lineage/advertisement proof transfer, pre-cleanup and pre-publication dirty guards, normal push cache invalidation and paired fingerprint update after publication/retirement. Do not cache push responses or count them as fetch cache misses.

Strict behavior follows from entering the **same** transaction after its one preparation step: `native.rs:1030–1065` keeps debt cleanup and quarantine with Full objects as alternates, strict native Git receive and its thin-pack completion, exact resulting refs, bounded compaction/import, and R14's coupled durability/publication code. No Git, ref mutation, GC, CAS, upload or DELETE occurs in planning. An ambiguous attempted receive/publication is never retried by the gateway; the current `StateStore`/SDK contract explicitly forbids fallback after attempted fused errors (`storage.rs:278–291`). Error paths must retain Native/DO dirty state and truthful receipts.

## Exact protocol and fallback rules

1. Add a **distinct receive opt-in capability**, dependent on strict first-read + generation-witness registration. Missing receive capability leaves R15 clients fetch-only. Present malformed/incompatible capability is rejected consistently with the pending R15 strict parser correction; do not enable from a truthy partial object. Warm providers do not enable receive prefetch. Durable decoding remains capability-independent.
2. Eligible public traffic is exact POST `/repo.git/git-receive-pack` with exact `application/x-git-receive-pack-request`, declared bounded original body ≤128 KiB, allowed identity encoding/protocol, no unsupported framing/transfer encoding and bounded canonical headers. Preserve original bytes, normalized header policy, method/target and request fingerprint/HMAC/witness bindings. Never reinterpret a fetch body as receive. The current `Logical::request` explicitly allows upload-pack only (`first_read.rs:140–190`); update its discriminant/validation narrowly, with separate authenticated request purpose/domain if needed.
3. **Before any authority-plus-GET dispatch**, planning conservatively parses supported receive command pkt-lines, flush and nonempty PACK framing. Exact `0000` returns unsupported before object I/O so the existing receive-noop shortcut remains. Unsupported valid commands/framing/encoding/protocol/body length, ref-only/no-PACK requests and default large streamed pushes go through the unchanged productive ordinary path, rather than a new rejection. Preserve the current exact empty-probe and default large-push API. Syntactic classification never replaces strict Git validation.
4. The receive plan selects **every current manifest pack**, with no lineage/prefix/have selection. Validate the complete snapshot descriptor graph before its first GET. The DO first-read path matches actual authoritative generation plus the **published** manifest fingerprint before reading objects; Native re-derives exact Full selection/current **local** fingerprint before consuming prefetched VerifiedChunks once. Keep the R15 `{generation,published,local}` fix: published durable garbage can differ from locally cleared garbage immediately after retirement. Hashing only the locally cleared manifest is incorrect and would lose this opportunity after every retirement.
5. Extend current stateless authenticated GZFR framing, bounded by 20-byte header + 1,500,000 metadata + 131,072 original + (16 MiB +2,060) bulk = **18,410,368 bytes**, safely below the retained 64 MiB incoming limit. Do not raise any cap or combine a maximum large push with a bulk frame. Payload retains ≤16 MiB, ≤256 entries and existing verified frame ordering. No oversized header transport, spool, session map or retained object-byte cache is introduced. Count any additional bounded key/config/fingerprint storage inside the existing joint budget.
6. Dirty/invalid/recovery state or missing exact authority fingerprint is unsupported before I/O. An existing partial codec view need not itself be fatal if the plan can freshly validate the complete authoritative manifest and the continuation reconstructs Full before producing its token; otherwise use ordinary recovery. Generation change returns no stale-plan GET bytes and follows the existing authoritative fallback. A local concurrent change after paid prefetch discards/charges that prefetch and uses explicit safe fallback **before** receive mutation. Crypto/frame/hash corruption is an error, not a hidden retry. Session replacement is checked at every async boundary.
7. The Worker/DO phase currently hardcodes `fetch` in `first-read.js:166`, and Native metrics do likewise. Receive must use push without relabeling observer/recovery work. Accepted receipts are aggregated exactly once before later body/auth processing can fail. Generation reads remain strongly consistent on every public Git request; no lease or stale-reference window is introduced.
