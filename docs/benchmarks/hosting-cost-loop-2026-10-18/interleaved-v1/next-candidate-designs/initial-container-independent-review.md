# Independent review: initial physical container

**A one-PUT path remains credible enough for a later, narrowly scoped falsification prototype. The current design needs corrections before that prototype; it is not an implementation or runtime approval.** No fixed-cost impossibility has been established. The advertised gain depends on keeping one genuine R2 PUT, exact logical ranges, unchanged SQLite allocation, and inexpensive durable translation across every legacy mutation path.

This review performed immutable Git reads, local source/input hashing, official documentation reads, and offline Python arithmetic only. It made no production edits, build, server/runtime invocation, fixture/Git-object generation, benchmark, push, CI, deployment, or delegation. Source is exact R20 `b74c91738a3fbfe3ebf30a936fbf9d7ff79f1ae0`; the observed checkout HEAD was `7d21233c1fac599baf20c3cbdfa84e4594ecac94`. The design's two SHA256SUMS entries, all 17 declared R20 blobs, and all 34 local declared input identities matched. [Input inventory](input-inventory/inventory.json) records exact identities; [offline arithmetic](input-inventory/receipt-arithmetic.json) and its [reproducer](input-inventory/recompute.py) accompany this review. Hashing an upstream context document does not approve its separate candidate.

## Original receipts and conservative margin

I independently reconstructed all 1,408 priced scheduled rows in the eight original R19/R20 reports, checked their 32-push/56-fetch identity, and checked another 704 separate warmup rows for identity/initial geometry. Frozen fixed-workload prices are **R19 $1.292455436180 and R20 $1.212471436180**, identically in both priced samples. These are scheduled-operation prices: existing startup and observer phases are excluded by the frozen objective. Any newly required startup/recovery work must still be exposed and debited when claiming an overall saving; it cannot disappear behind that exclusion. R2 peak is held once for 30 days, never multiplied by 1,000.

Both 64 MiB profiles, both priced samples, have exactly three initial PUTs and **34,207,816 B** written. The final manifest's original root pack is 34,181,516 B plus a 26,300 B index. Its original logical ranges are:

The initial receipts show five DO requests, eight SQL written rows, three Worker requests, three R2 PUTs, and zero R2 GET bytes per 64 MiB first push. The two 16 MiB profiles start with one 8,544,710-byte PUT. Current `lib.rs:118–158` really already bundles pack and index; this proposal changes their physical upload representation while preserving logical descriptors.

Four removed PUTs across one all4 repetition, repeated 1,000 times, have **$0.018** Class-A credit, or **1.4845710557%** of R20. The 1% target is **$0.0121247143618**. After conservatively charging two additional HTTP Worker requests ($0.0006), remaining headroom is **$0.0052752856382**. No saved SQL, DO, socket rotation, Class-B, or byte-price credit is granted here.

One extra operation across an all4 repetition costs, after repetition: Class A $0.0045; Class B $0.00036; Worker $0.0003; DO $0.00015; SQL written row $0.001; SQL read row $0.000001. Thus two added Class-A operations, or six added SQL written rows, fail this conservative case. A separate map row rewritten on every one of 32 pushes in each 64 profile costs $0.064 before other work and is immediately unsuitable under this model. A map installed once and preserved without a separate per-push write is still plausible. A two-Class-A successful route in both 64 profiles loses the advertised four-PUT case; its $0.009 Class-A saving alone is below target. Any alternative credit would need independent evidence.

## Required design corrections

1. **Specify the 30-second gate deadline.** R20 `cloudflare/src/index.js:1638–1669` holds `ctx.blockConcurrencyWhile` throughout service I/O. Cloudflare documents a **30-second callback timeout that resets the DO**, distinct from a connected HTTP request's otherwise unlimited wall time. At 1 MiB/s, this body alone takes **32.62311554 seconds**; the minimum rate to finish within 30 seconds, ignoring all hashing, storage, SQL and cancellation, is 1,140,260.53 B/s. The design must require a total deadline with explicit cleanup reserve below 30 seconds, or separately review a different serialization mechanism. An idle timeout alone permits an indefinitely slow progressing sender. Cancellation/draining must terminate before gate release; timeout/reset stays ambiguous and cannot trigger fallback or resend. This needs an exact pinned-runtime slow/stalled-body test. [DurableObjectState](https://developers.cloudflare.com/durable-objects/api/state/#blockconcurrencywhile), [DO wall-time limits](https://developers.cloudflare.com/durable-objects/platform/limits/#wall-time-limits-by-invocation-type).

2. **Match eligibility to map capacity.** `16 MiB < total <= 64 MiB` allows two, three, or four original logical chunks. A fixed three-tuple map cannot cover totals above 48 MiB. Either narrow this candidate to its three-range geometry, or explicitly support/own/price four tuples and revise all bounds. The measured 34,207,816-byte case has three; no fourth-range saving or safety is established by these receipts.

3. **Freeze a concrete durable format and cost ledger.** Define exact storage-index/catalog versions, schema operations, encoded byte widths, namespace rules, and every SQL statement on creation, reopen, ordinary PUT/CAS, retirement and GC. Existing inline v1 (`inline-catalog.js:7–48`) and deferred page v2 (`catalog-pages.js:31–46,59–80`) reject physical members above 16 MiB. Existing normalized page v1 can encode larger sizes, but that is not a transparent way to retain deferred acknowledgments or inline semantics. Extend all encode/decode/aggregate/reopen/demotion/rebuild paths deliberately. A new field must not turn every ordinary publication into two written rows. Measure the exact state at manifest growth boundaries and the frozen final 4,923-byte 64-profile manifest; do not infer page allocation from logical JSON size. SQLite pricing is by actual rows and stored data; retain actual cursor counters and databaseSize. [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/#sqlite-storage-backend).

4. **Make post-PUT uncertainty survive DO reconstruction.** Atomic post-PUT installation of manifest + map + physical catalog + peak is the right publication invariant, but does not by itself cover a PUT-success/pre-SQL crash. R20 reconstructs with `catalogCertain = true` (`index.js:597`) and restores durable catalog state (`685–743`); an empty catalog alone cannot distinguish physical emptiness from an unrecorded container. Specify either a synced pre-PUT pending-intent/uncertainty owner, with its actual writes charged, or an enforced recovery invariant covering every fresh and surviving Native/DO path before any later mutation or DELETE. Reuse an already paid authoritative startup inventory where valid; do not silently add a free LIST or assume all old callers run a new recovery protocol. A pending record must never authorize a read or publication before successful completion. A committed map and manifest cannot be separated. Recovery must retain and checkpoint all distinct physical bytes before deletion, including orphan, duplicate and failed-delete survivors. Missing map plus a committed container manifest is uncertainty requiring fail-closed reconciliation, not a reason to delete unknown keys.

5. **Finish the physical/logical retirement state machine.** Derive physical reachability from the current authoritative manifest and durable map. A logical alias retirement does not remove bytes while another mapped member is live. Specify all/some/none live, tombstone/resurrection, equal-content legacy PUT, standalone duplicate, stale CAS/GC, failed DELETE, and catalog-debt replay. Do not mutate the immutable mapping of a live key. If a duplicate standalone object is actually created, count its full distinct bytes and pre-delete coexistence peak. If an equal-content PUT is safely elided, report zero physical PUTs truthfully and do not issue today's one-PUT proof. Existing proof `retirement-proof.js:25–46` requires one physical DELETE per logical debt key and one physical PUT for a coupled upload; its HEAD reconciliation also compares logical-key physical objects (`index.js:799–809`). It cannot certify range alias retirement. Supply a reviewed physical-debt proof or suppress proof and price actual recovery calls. Keeping only the tail retains **33,554,432 B** of slack; evacuation adds writes and peak. A universal lifetime 1% guard is unproved.

6. **Do not substitute a final manifest for an intermediate inventory proof.** Each original priced trial has only one manifest observation in raw rows: a **final generation-32 manifest attached to `push_01`**. `push_sequence_object_stats` is null. The final root's three original chunks remain live, which supports the narrow workload hypothesis, but does not prove every intermediate manifest/physical inventory or fault state. Top-ten key counters, even with `truncated:false`, are not an exhaustive timeline and can reset across DO instances. Preserve this as an explicit missing proof. A later cheap runner needs bounded intermediate liveness and distinct-physical inventory evidence before any guard claim.

7. **Make the rollback boundary operational.** Old Native + new Worker must support ordinary repositories and container repositories through logical read, PUT, retirement and GC translation. Any Native + unchanged Worker on container storage is unsafe: old GC `index.js:1550–1605` lists the repository prefix and compares physical keys directly with logical `live_keys`. A different child namespace under that same listed prefix does not protect the container. Specify a version-aware deployment/DO and R2 prefix boundary that the old Worker cannot mutate, or a reviewed migration. Unknown-schema rejection in one new decoder alone is not rollback protection. No deployment is authorized here.

## Streaming and authority conditions that remain plausible

The single-PUT idea is technically credible: the official R2 API accepts ReadableStream PUT values, a SHA-256 verification option, exact range options and returned range metadata, and its single-part size limit exceeds this object. The independently rehashed installed Miniflare 4.151-associated source has separate `put`/multipart handlers and a streaming digest path (`bucket.worker.js:971–994,1106–1139`), not an implicit multipart conversion. These are API/source facts, not a one-request, allocation or pinned-runtime execution proof. Installed 4.116/4.151 evidence does not establish exact R20-locked **Wrangler 4.149.0** behavior. [Workers R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), [R2 size limits](https://developers.cloudflare.com/r2/platform/limits/).

For a future route, start consumption of `FixedLengthStream.readable` by the single R2 PUT concurrently with pumping into its writer; awaiting PUT before starting the pump deadlocks. Split source chunks at logical boundaries and scratch limits, await digest and downstream writes, and close/compare each logical digest before progressing. Close the downstream writer only after EOF, exact total and all logical digests are established. Await pump, final hash and provider completion before the SQL publication. On either-side failure, cancel the upstream, abort the writer, observe the R2 promise, and retain ambiguity/unknown accounting where completion cannot be established. A default-reader chunk's original backing allocation can exceed a small scratch view: proving BYOB or bounded upstream queues matters, not merely slicing to 64 KiB. Do not use a full-body collector or an independently advancing tee. FixedLengthStream enforces known length but does not prove bounded provider queues. [FixedLengthStream](https://developers.cloudflare.com/workers/runtime-apis/streams/transformstream/#fixedlengthstream), [DigestStream](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/).

Native must determine eligibility and construct the exact complete next manifest **before ordinary `stage_bundled_pack` dispatches its first PUT** (`native.rs:1421–1423`; `lib.rs:141–156`). The current pack/index locals are dropped before final publication (`native.rs:1402–1462`), so retaining borrowed slices for a fused final request needs an explicit lifetime/owner change. Count capacity and overlap with metadata, proofs, cache, receive body, HTTP buffers and response owners. No concatenating Vec or enlarged socket message is permitted. The 64 MiB Git receive limit, 128 MiB snapshot limit, logical 16 MiB response limit, 32 MiB/256-entry joint owner budget, pool32, and 262,144-byte socket reservation remain unchanged. This is an explicit exception/new contract for **internal physical upload**, not an increase in Git receive or snapshot limits and not adherence to the old 16 MiB physical-upload contract.

Authenticate bounded canonical metadata before DO dispatch, with a domain-separated version/method/route/session/repository MAC over the exact generation, complete manifest, total/physical digest and ordered mapping. Check current registration after asynchronous validation, reject stale/nonempty/debt state before PUT, consume the dispatch capability before I/O, and never reinterpret an attempted error as side-effect-free Unsupported. A small header fits the proposed bounds in the observed first snapshot, but exact encoded maximum and all owners remain to be fixed. An unacknowledged PUT is not an uploaded-success receipt.

Every logical GET, including bulk first-authority and scalar legacy reads, must request only its exact range and verify total, offset, returned length and logical SHA before Native cache/materialization. Cancel invalid range metadata before collecting a body; bound consumed length and reject ignored range, truncation, excess and wrong digest. Never download the whole container and slice it. The mapping can remain opaque to the manifest fingerprint only while it is immutable/durable and each original logical payload is independently authenticated. Preserve order, repeated keys, masks, token invalidation, authority and paid-discard semantics. A private <=16 MiB logical allocation cannot retain a 34 MiB backing buffer.

Existing `operation()` accounts write/read byte totals on successful callbacks only (`index.js:632–663`); it is not sufficient evidence for partial-stream consumption after failure. Track binding attempts and actual known consumption separately, and leave the relevant accounting incomplete/unknown when reset, cancellation or provider failure obscures it. Do not report a failed partial stream as a measured zero-byte transfer. Multipart remains unattractive to this hypothesis: create + three parts + complete is five Class-A calls. AbortMultipartUpload is R2-free under current pricing; its other service work and incomplete storage are still real. [R2 pricing](https://developers.cloudflare.com/r2/pricing/).

## Smallest useful later falsification gate

**Recommendation only; none of this was implemented or run.** After a docs-only correction and separate authorization, use one Rust runner, exact pinned runtime and existing ordinary fixtures. Keep fit-response and deferred-bootstrap work independent and reprice against whichever predecessor is actually selected.

1. First freeze the compact map/catalog codec and exact SQL plan. Exercise creation, reopen, inline demotion and final-manifest-size persistence without an optimization benchmark. Reject any extra SQLite allocation beyond 24,821.76 B in a comparable profile, or a conservative ledger that exceeds the remaining $0.0052752856382. This is cheaper than a full cost screen. Do not invent intermediate manifests from the final receipt.
2. Run one fresh ordinary64 initial push and an ineligible ordinary16 control. Include zero-read warm behavior. Compare cache admission, masks, authority/token behavior, Git bytes and HTTP bodies to control.
