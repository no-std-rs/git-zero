## Stronger opportunity: one protected verified immutable chunk

A concrete common policy is **retain the first successfully verified GET chunk in one protected slot**, at most16MiB, until budget pressure forces eviction; never populate it from PUT, an extra probe, startup warming or out-of-timer work. The slot survives pushes because its digest identifies immutable bytes; response entries still invalidate on pushes. It shares the existing32MiB owning-allocation budget and256-entry ceiling with responses, certificates and R17's256KiB socket reservation. This is a bounded admission policy, not an unlimited map or ordinary scan-thrashing LRU. It does not select a fixture hash, branch, generation or benchmark mode.

Actual complete R15 cold reports, in both measured samples, have **79 positive-GET timed operation rows** per profile,425/585 total GETs for16/64MiB. The retained initial pack is included by every Full and historical-prefix read. Its first chunk is8,544,710/16,777,216 bytes. Conditional on admission surviving and cache-aware planning, one initial GET admits it and78 subsequent selected reads per profile can reuse it: **156 GETs × $0.00036 = $0.05616** per1,000 four-profile replays from ClassB alone. This is source/readset inference over actual operations, not a new measurement or a subtraction of recent per-instance key counters, which reset on DO eviction. It is about3.74% of the illustrative postR17 denominator below. No DO callback, socket Upgrade or read-byte saving is credited in that dollar figure, although eliminating the64MiB full-chunk bin also appears promising.

The actual maximum retained response bytes at recorded fetch boundaries are12,824,068/12,815,525. Adding the protected chunk and256KiB socket reservation leaves **11,923,510 /3,699,547 bytes** within32MiB before certificates, allocation headers, alignment, temporary retention and other metadata. This boundary arithmetic is promising **not an owning-allocation or peak-memory proof**. Retain exact Arc/allocation capacities, not just slice lengths; an Arc owning a larger bulk frame must charge that entire allocation. Bound copies during admission and materialization. Charge the new protected slot against the entry limit. If it loses admission, response-cache hits or more expensive callbacks, the proven net lower bound is presently **zero**. The `$0.05616` is the protected-once cohort scenario; it is not an unconditional net bound.

Cold behavior still discards the Git codec view and authenticates the current manifest before cached data can be consumed. Admit GET data only. Every normal latest fetch after a successful push naturally needs the new uncached chunk/output, so continues actual positive R2 GETs; initial latest admits from its real GET. Push/historical reads may legitimately become all-cache. No dummy GET, forced probe, selective no-cache benchmark branch or fabricated R2 receipt is allowed. Shared digest keys can survive ref changes and retirement, but current authenticated manifest membership, exact declared length and verified ordered reconstruction still govern use. Cache hits do not grant a stale generation witness or hide missing paid receipts for noncached work.

**Required interface amendment:** caching only inside Native's later bulk reader is insufficient because R15/R16 may already have fetched the protected chunk in the gateway's prepared first batch. Current first-batch validation requires a nonempty list: an all-cache preparation must either use a versioned authority-only continuation, or return unsupported before storage work and use the existing ordinary authority check followed by cached reconstruction. Do not invent an empty bulk proof or remove the authority check. A unique new Native tree actually producing/consuming this plan makes common-Worker capability attribution substantive.

## Narrow candidate: fresh schema and initial inline ownership

Actual completed R14 and R15 reports have the same SQL pattern:16MiB first push **4 written rows**, total35;64MiB first push **8**, total39. All31 later pushes write exactly one row. Each observed startup separately writes **6 rows** and uses2 Worker service/DO calls. First push SQLite is20,480 bytes, final24,576. R14 atomically couples the final PUT catalog and CAS, so the old separate PUT/CAS260-row floor is invalid.

Source explains the first-push overhead: three ALTERs add peak/page/inline columns;64MiB additionally transfers the initial root-page owner into repository_state with an insert/update plus catalog delete. A coherent fresh-bootstrap design can target first-push1/3 rows and totals32/34: create final columns directly in the **same three existing CREATE statements**, and install the empty inline owner on the first standalone upload so it never needs root-page promotion. This saves **3+3+5+5 =16 rows = $0.016** across four profiles. The fourth-profile number is conditional: completed R15 64warm does not exist in this failed attempt.

Use an authenticated, versioned Native bootstrap **instead of the initial manifest-load RPC**, returning schema acknowledgment plus authoritative manifest. Defer schema choice until that first request; ordinary old Native's manifest GET selects legacy initialization. Bootstrap constructs final-column versions of repository_state/blob_catalog/high_water, with **no eager repository singleton/root insert**. Existing initialized stores never reset or drop tables; return existing-format acknowledgment and retain ordinary paid migrations. Subsequent recovery uses ordinary manifest loads and generation-checked physical GC. An uninitialized SQL store does not imply an empty R2 bucket: existing startup GC must still preserve an orphan-observed peak before deletion.

After registration, the first eligible standalone PUT on a genuinely empty owner may initialize the bounded inline root; its actual successful R2 PUT is followed by one unpublished generation0 state UPSERT carrying size/peak, replacing the existing catalog-row write. The second initial PUT updates it once; final upload+CAS remains R14's atomic transaction and sync-before-retirement. No metadata-only root seed is free. Keep32-member/8192-manifest/16MiB-chunk limits and demote on unsupported shape. Missing/lost PUT/catalog/sync/CAS replies remain dirty and force physical reconciliation before later mutation. Older Native with the new Worker must decode durable ownership after registry loss/restart; old Worker rollback remains a migration boundary.

This requires an explicit production startup-protocol amendment and meaningful Native implementation. An always-modern Worker constructor alone changes every provider under the current common Worker; a cosmetic Native change cannot attribute it. Candidate Native must actually request/validate bootstrap and early-owner semantics, while legacy Native keeps the old path under that **same Worker**. Preserve fixture/reference/timed schedule identity and expose startup/observer/physical receipts separately. This must be a real reduction in schema work, not a shift of ALTERs to an excluded phase.

**Exact first production-workerd gate:** before attempting a full implementation/screen, run fresh old/candidate initialization plus one real16MiB and64MiB push through the production service bridge with Rust driving it. Candidate must retain startup **6 written rows and2 service/DO calls**, then first pushes **1/3 written rows**, with the same1/3 actual PUTs, one attempted/winning CAS, bytes, peaks and subsequent32/34-row pattern. Capture actual cursor receipts including CREATE/ALTER/promotion, no observer-induced preinitialization, and full physical totals. Reject if an added bootstrap RPC, singleton seed, schema page, observer repair or hidden migration is needed. Repeat on existing legacy/page/inline repositories and reopen; require current24,576-byte final guard, no larger caps and no read-only promotion.
